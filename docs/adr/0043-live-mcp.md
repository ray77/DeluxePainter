# ADR-43: Live MCP, part 1: the Workspace, the new tool set, the local HTTP server and the stdio bridge

- Status: accepted (2026-11-12, wave 8 "live MCP", part 1 of 3: `dpx-mcp` core, HTTP server, bridge). The GUI side (the GUI `Workspace`, Prefs > AI & MCP, `--mcp`, the status display) is part 2; layers and generation tools come with the integration step. Nothing visible changes in this part, so nothing was asked; every point below was decided without the owner.
- Supersedes: ADR-5's "local socket / named pipe (interprocess crate)" bridge (the bridge now speaks MCP Streamable HTTP to the app), and ADR-21's "the GUI never opens an MCP channel" (the GUI will run a local HTTP server, but only while the user turns it on in Prefs > AI & MCP; it stays off by default). ADR-21's tool names (`app_status`, `new_document`, `get_document_state`, `draw_*`/`open_*` of ADR-24…) are removed, not aliased.
- Context:
  - MCP clients (Claude Desktop, Claude Code) should drive the **running** app, not only a private headless engine, and see the result live. The editor state is owned by one thread (the GUI's `logic()` in the app, a worker thread headless), while rmcp serves requests concurrently on tokio.
  - Clients launch stdio servers themselves; the running app cannot be one. So a stdio process has to forward to the app, and it must work whether the app is running or not.
- Decision:
  - **Workspace (`dpx_mcp::workspace`):** a trait over the editor state the tools need: the engine of the shown page, `execute`/`undo`/`redo`, `replace_picture` (not undoable), the shown slot and the spare page (`spare`, `set_spare_page`, `swap_spare`), the brush (`set_brush`, `brush_size`), the picture name and saved state (`mark_saved` with the revision), `project_extras`, `bg_color`, `ask(question, reply)` and `log`. `HeadlessWorkspace` implements it with two pages; its spare follows the GUI's `take_spare` rules (a spare of another format is replaced by a blank one of the picture's format) and `ask` answers "no". The GUI implementation is part 2.
  - **Jobs (`dpx_mcp::jobs`):** a tool's state access is a boxed `FnOnce(&mut dyn Workspace) + Send` sent over a std `mpsc` channel with a tokio oneshot for the reply (`Executor::run`). The owner thread runs them: `JobQueue::run_pending` (the GUI, once per frame, after a wake callback asked for a repaint) or `run_until_closed` (headless). A job runs inside `catch_unwind` (a panic becomes `INTERNAL_ERROR`, the owner thread survives); a job not answered in 60 s gives `APP_BUSY`; a closed queue `APP_UNAVAILABLE`. `Executor::ask` (overwrite questions) has no timeout, the user may take time. File reading/writing, PNG encoding/decoding and import conversion run in `spawn_blocking` on the server side; jobs only touch state, so a frame never waits for disk or a big conversion.
  - **Arrival order (`dpx_mcp::seq`):** every `tools/call` and `resources/read` takes a ticket when it arrives (stdio: in the transport's `receive`, `server::Ticketed`; HTTP: in the guard middleware, before rmcp sees the request) and holds its turn for the whole call, so calls are fully serialised in arrival order even when a client pipelines them (fixes ADR-21's consequence "may be answered out of order"). A cancelled or dropped call releases its place. `initialize`, `tools/list` and `resources/list` take no ticket.
  - **Tools (21):** `get_app_status`, `list_documents`, `get_document_info`, `create_document`, `select_document`, `get_palette`, `set_palette_color`, `draw_pixel`, `draw_line`, `draw_rectangle`, `draw_ellipse`, `fill_area`, `import_image`, `undo`, `redo`, `save_project`, `export_image`, `get_preview`, `open_picture`, `execute_command`, `get_pixels`. Arguments are strict (`deny_unknown_fields`, an unknown argument is `INVALID_ARGUMENT`). Annotations: read-only, destructive (import_image, open_picture, save_project, export_image) and idempotent hints; `openWorldHint` false.
  - **Results:** every result is a JSON object with `success`, and `document_id` and `revision` where a document is involved; it is the structured content and also the text block (clients that ignore structured content still get it). Errors are `{success: false, code, message}` with `isError: true` and stable codes (`INVALID_ARGUMENT`, `PALETTE_RANGE_INVALID`, `HARDWARE_LIMIT`, `UNSUPPORTED_MODE`, `DOCUMENT_NOT_FOUND`, `REVISION_CONFLICT`, `NOTHING_TO_UNDO`/`NOTHING_TO_REDO`, `PERMISSION_DENIED`, `FILE_ACCESS_OFF`, `PATH_NOT_ALLOWED`, `FILE_EXISTS`, `OVERWRITE_DECLINED`, `FILE_NOT_FOUND`, `DIR_NOT_FOUND`, `NOT_A_REGULAR_FILE`, `INVALID_FILE`, `UNSUPPORTED_FILE_TYPE`, `IO_ERROR`, `APP_NOT_RUNNING`, `APP_CONNECTION_LOST`, `APP_BUSY`, `APP_UNAVAILABLE`, `INTERNAL_ERROR`). An unknown tool is a JSON-RPC `invalid_params` error, not a result. `get_preview` returns the PNG image block first, then the JSON.
  - **Documents:** the picture and the spare page have the ids `page1` and `page2`; an id follows its page across Spare > Swap, so "page1" always means the same page. `select_document` swaps (like Picture > Spare > Swap); selecting the active page changes nothing (idempotent). Tools work on the active page; `get_document_info` accepts either id.
  - **create_document:**
    - Size and mode: an explicit `resolution`/`video`/`interlace` wins; otherwise a size that is exactly a standard screen gets that mode, else the first mode whose screen holds the size in the order Low Res, High Res, SuperHiRes, non-laced before laced, PAL before NTSC, with a custom screen of exactly the size (so 320×240 is PAL:Low Res with a custom 320×240 screen, and the result notes it). Presets `ntsc_lores`, `pal_lores`, `pixelart_320x240`, `ntsc_hires`, `pal_hires`, `ntsc_interlace`, `pal_interlace`.
    - Hardware limits are refused with a message that says why and what works: OCS High Res with 32 colours gives `PALETTE_RANGE_INVALID` "OCS PAL:High Res shows at most 16 colours at once, not 32 … use 16 colours, Low Res (32 colours) or AGA (256 colours)". Nothing is reduced silently.
    - It runs the engine's `SetFormat` (undoable, `undoable: true`) when the chipset stays and the document has one frame. `SetFormat` has no chipset field and this part does not add one: a chipset change (or a multi-frame document) makes a blank document and replaces the picture (`replace_picture`, not undoable, `undoable: false` and a note in the result). The integration step may move this to a chipset-aware `SetFormat` (ADR-46).
  - **set_palette_color:** `#RRGGBB` (or `#RGB`, each digit doubled); on OCS a colour that is not 12-bit (each channel a multiple of 0x11) is refused with `HARDWARE_LIMIT`, naming the nearest 12-bit colour, instead of rounding it.
  - **Drawing:** `draw_*` and `fill_area` take a palette index (checked against the palette size) and draw with a 1-pixel brush through the engine's `Shape`/`Stroke`/`FloodFill` commands, one undo step each. `execute_command` runs any raw `dpx-core` command with optional `expected_revision` and `dry_run`.
  - **import_image:** a path in an approved directory or base64 data (a `data:` URL is accepted), at most 12 MiB of data and 64 Mi pixels (`MAX_IMPORT_PIXELS`); PNG (indexed or true colour) or JPEG only. Options are ADR-42's (`position` centre/top_left, `palette` new/current, `colors`, `dither` none/floyd_steinberg/ordered), through `dpx_core::import`. Targets: `picture` (replaces the page like Load, not undoable), `spare` (the spare page in the picture's format and palette) and `brush` (the picture's palette, its own size, transparent colour 0 when the source has transparency). The conversion runs outside the owner thread; a change of the document meanwhile gives `REVISION_CONFLICT` instead of a picture made for an older palette.
  - **Files:** only in approved directories (ADR-24, `FileAccess`). `save_project` writes `.dpxproj` only (with the spare page and project extras) and marks the page saved; `export_image` writes IFF ILBM (`.iff/.ilbm/.lbm`), IFF ANIM (`.anim`) or indexed PNG, chosen by the extension or `format` (a mismatch is `INVALID_ARGUMENT`), validated against the chipset's limits. An existing file needs `overwrite: true`; the overwrite setting then either allows it or asks the user through `Workspace::ask` (headless: "no", `OVERWRITE_DECLINED`). `open_picture` opens ILBM, ANIM, indexed PNG or a `.dpxproj` (with its spare page); true-colour PNG and JPEG are refused with a pointer to `import_image`.
  - **One picture read:** `get_preview`, `get_pixels`, `export_image` and the resources read the page through `tools::visible_picture` only, so the integration step can return the visible layer composite there (ADR-44).
  - **Resources:** `dpx://document/info` (JSON, as `get_document_info`), `dpx://document/palette` (JSON) and `dpx://document/preview.png` (base64 PNG blob); the server announces the resources capability. No subscriptions.
  - **Permissions and activity (`dpx_mcp::state`):** `Settings { read, edit, overwrite: Allowed|Ask, access }` behind an `Arc<ServerState>` the GUI can change while the server runs; a refused call says "… is turned off for AI clients (Prefs > AI & MCP)". `Activity` counts requests and tool calls and keeps the last request time and the client's name (from `initialize`), for the GUI's status display. Headless modes allow read, edit and overwrite.
  - **HTTP server (`dpx_mcp::http`):** rmcp's Streamable HTTP service on axum 0.8 (features `tokio`, `http1` only), bound to `127.0.0.1` only, path `/mcp`, default port 8765, else the next 10 ports, else any free port (`--port 0`: any). Stateless (`NeverSessionManager`, no `Mcp-Session-Id`), JSON responses (no SSE stream). It runs on its own thread with its own tokio runtime and stops on a `CancellationToken` (`HttpServer::stop` waits at most 3 s and removes the endpoint file; `Drop` does the same). A guard middleware checks, in this order: `Host` must be `127.0.0.1:<port>` or `localhost:<port>` (else 403; against DNS rebinding); any `Origin` header is 403 (browsers send it, local MCP clients do not); `Authorization: Bearer <token>` compared in constant time over the whole token (else 401 with `WWW-Authenticate: Bearer`); a body announced above 16 MiB is 413 before it is read, and a body read beyond 16 MiB too. rmcp's own Host/Origin checks are on as well.
  - **Token and discovery:** the token is 32 random bytes (`getrandom`) as 64 hex digits, new for each start, or `DPX_MCP_TOKEN` (at least 16 visible ASCII characters) for the headless HTTP mode. The server writes `<config dir>/mcp-endpoint.json` `{version: 1, port, token, pid, app_path, url}` atomically (temporary file + rename) with mode 0600 on Unix, and removes it on stop only if it still names this process and port. `<config dir>/mcp-app.json` `{version, app_path, args}` (default args `["--mcp"]`) stays when the app stops: it tells the bridge what to launch; the GUI writes it when its server starts (part 2). The config directory is the one `settings.json` uses (`DPX_CONFIG_DIR`, else `~/Library/Application Support/DeluxePainter` on macOS, `%APPDATA%\DeluxePainter` on Windows, `$XDG_CONFIG_HOME` or `~/.config` + `/DeluxePainter` elsewhere); it lives in `dpx_mcp::paths` and the app's `config::default_dir` calls it, with a test that both agree.
  - **CLI:** `deluxepainter mcp [--allow-dir DIR]...` (stdio, as before, now with the new tools and arrival order); `deluxepainter mcp --http [--port N] [--allow-dir DIR]...` (the headless HTTP server; it prints the URL and the endpoint file's path on stderr, never the token, and stops on Ctrl-C or SIGTERM, removing the endpoint file; without a config directory it needs `DPX_MCP_TOKEN`, else it refuses to start because no client could learn the token); `deluxepainter mcp-bridge` and the separate binary `dpx-mcp-bridge` (no arguments).
  - **Bridge (`dpx_mcp::bridge`):** a stdio MCP server for clients that only launch processes. It answers `initialize`, `tools/list` and `resources/list` itself from the same definitions (so a client sees the tools while the app is not running), and forwards `tools/call` and `resources/read` with rmcp's Streamable HTTP client to `127.0.0.1` only, with the token from the endpoint file. It re-reads the endpoint file whenever it (re)connects and reuses its connection while the file is unchanged. With no reachable app it launches the one named in `mcp-app.json` and waits up to 20 s for a new endpoint file; otherwise the call's result is `APP_NOT_RUNNING` "DeluxePainter is not running. Start it and turn on Prefs > AI & MCP." A read-only call is retried once after a lost connection; a changing call is not (it may have run) and gives `APP_CONNECTION_LOST`. The app sees the client as "<client name> via deluxepainter-bridge". The bridge keeps arrival order itself (one ticket per call) and stdout carries protocol only. `apps/dpx-mcp-bridge` is a small crate without eframe, so a client config can point at a binary that starts fast.
  - **Dependencies (all permissive, checked in `cargo metadata`):** direct: `axum` 0.8 (MIT), `getrandom` 0.3 (MIT OR Apache-2.0, already in the tree), `tokio-util` 0.7 (MIT, already in the tree), rmcp features `transport-streamable-http-server`, `client`, `transport-streamable-http-client-reqwest` (rmcp: Apache-2.0). New in `Cargo.lock`: axum, axum-core, http-body, http-body-util, hyper, hyper-util, tokio-stream, tower, tower-http, tower-layer, tower-service, try-lock, want (MIT); matchit (MIT AND BSD-3-Clause); sync_wrapper (Apache-2.0); chacha20, http, httparse, httpdate, ipnet, mime, rand, rand_core, reqwest, sse-stream, wasm-streams (MIT OR Apache-2.0). No ISC-only crate was added.
- Verified (macOS, local, `cargo test --workspace`):
  - `dpx-mcp` unit tests: the tool definitions and strict arguments, `create_document` rules (320×240, OCS High Res with 32 colours refused, mode inference, presets, undoable vs. replacing), OCS palette refusal with the nearest colour, drawing, `execute_command` dry run, permissions, previews, `import_image` to picture/spare/brush and on OCS, save/export/overwrite/reopen, file access off, resources, activity; the sequencer (order, dropped tickets), the job queue, the headless spare rules, the endpoint file (round trip, 0600, removal only by its owner), the config directory rules per platform (through injected environment), port fallback and the token comparison.
  - `apps/deluxepainter/tests/mcp_stdio.rs` (the real `deluxepainter mcp`): handshake, list, calls with the new names, the 320×240 example, paint/look/undo/files, coded argument errors, HAM/EHB pictures, missing `--allow-dir`, resources, and 24 calls written at once behind a slow import answered in arrival order (revisions 1…24).
  - `apps/deluxepainter/tests/mcp_http.rs` (the real `deluxepainter mcp --http`): handshake, list and calls over HTTP; 401 for a missing, wrong or almost-right token; 403 for a foreign `Host` and for any `Origin`; 413 for an announced 17 MiB body; pipelined calls on separate connections in arrival order; files only in the approved directory; SIGTERM stops the server and removes the endpoint file; refusal without a config directory or token; the bridge (`deluxepainter mcp-bridge`) forwarding stdio to it; the bridge launching the app named in `mcp-app.json`.
  - `apps/dpx-mcp-bridge/tests/bridge.rs` (the real `dpx-mcp-bridge` against the library's HTTP server): forwarding of calls, tool errors and resources, the client name, reconnecting to a restarted server with a new port and token, `APP_NOT_RUNNING` without an app and with a stale endpoint file, bad arguments.
- Not verified:
  - Real clients: Claude Desktop, Claude Code, MCP Inspector, neither through the bridge nor directly over HTTP; in particular whether a client's HTTP stack sends an `Origin` header (it would get 403).
  - Windows and Linux (build, tests, the endpoint file's permissions: on Windows it relies on the profile directory's ACL, no 0600 equivalent is set), and macOS app bundles as `app_path`.
  - The stateless `2026-07-28` protocol era (only `initialize`-based clients were exercised).
  - The GUI side: the GUI `Workspace`, `JobQueue::run_pending` in `logic()`, `--mcp`, Prefs > AI & MCP, writing `mcp-app.json` (part 2). An `.mcpb` bundle for Claude Desktop is not built.
- Consequences:
  - The app can be driven live once part 2 lands; the bridge works today against the headless HTTP mode.
  - hyper/axum/reqwest enter the app binary; the bridge binary carries them too but not eframe.
  - Anyone who can read the user's config directory can read the token and call the app; that is the same trust boundary as `settings.json` and the user's files.
