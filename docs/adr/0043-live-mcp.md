# ADR-43: Live MCP: the Workspace, the tool set, the local HTTP server, the stdio bridge and the running GUI

- Status: accepted (2026-11-12, wave 8 "live MCP"). Part 1 of 3: `dpx-mcp` core, HTTP server, bridge. Part 2 of 3 (section "Decision, part 2" below): the running GUI as the workspace, the `mcp` settings section, `--mcp`, the server's lifecycle, the overwrite question, the activity log. Part 3 of 3 (section "Decision, part 3"): Prefs > "AI & MCP..", the connect flows for Claude Code and Claude Desktop, the `.mcpb` extension and its CI build; layers and generation tools come with the integration step. Part 1 changes nothing visible. Part 2's only visible change is the "Replace File?" question in the existing choice requester (ADR-34), worded as the wave's brief asks. The owner decided the menus (Prefs > "AI & MCP..", English strings) for the wave; the requester's layout and wording and the points listed under "Decided without the owner" in part 3 were not asked.
- Supersedes: ADR-5's "local socket / named pipe (interprocess crate)" bridge (the bridge now speaks MCP Streamable HTTP to the app), and ADR-21's "the GUI never opens an MCP channel" (the GUI will run a local HTTP server, but only while the user turns it on in Prefs > AI & MCP; it stays off by default). ADR-21's tool names (`app_status`, `new_document`, `get_document_state`, `draw_*`/`open_*` of ADR-24…) are removed, not aliased.
- Context:
  - MCP clients (Claude Desktop, Claude Code) should drive the **running** app, not only a private headless engine, and see the result live. The editor state is owned by one thread (the GUI's `logic()` in the app, a worker thread headless), while rmcp serves requests concurrently on tokio.
  - Clients launch stdio servers themselves; the running app cannot be one. So a stdio process has to forward to the app, and it must work whether the app is running or not.
- Decision:
  - **Workspace (`dpx_mcp::workspace`):** a trait over the editor state the tools need: the engine of the shown page, `execute`/`undo`/`redo`, `replace_picture` (not undoable), the shown slot and the spare page (`spare`, `set_spare_page`, `swap_spare`), the brush (`set_brush`, `brush_size`), the picture name and saved state (`mark_saved` with the revision), `project_extras`, `bg_color`, `ask(question, reply)` and `log`. `HeadlessWorkspace` implements it with two pages; its spare follows the GUI's `take_spare` rules (a spare of another format is replaced by a blank one of the picture's format) and `ask` answers "no". The GUI implementation is part 2.
  - **Jobs (`dpx_mcp::jobs`):** a tool's state access is a boxed `FnOnce(&mut dyn Workspace) + Send` sent over a std `mpsc` channel with a tokio oneshot for the reply (`Executor::run`). The owner thread runs them: `run_until_closed` (headless) or, in the GUI, one by one with `JobQueue::take`, which may also hold a job (`hold`, it stays first) or refuse it without running it (`Job::refuse`, part 2). A job runs inside `catch_unwind` (a panic becomes `INTERNAL_ERROR`, the owner thread survives); a job not answered in 60 s gives `APP_BUSY` and is dropped, it never runs later; a closed queue `APP_UNAVAILABLE`. `Executor::ask` (overwrite questions) waits for the user at most `ASK_TIMEOUT` (45 s) plus a 15 s margin (part 2). File reading/writing, PNG encoding/decoding and import conversion run in `spawn_blocking` on the server side; jobs only touch state, so a frame never waits for disk or a big conversion.
  - **Arrival order (`dpx_mcp::seq`):** every `tools/call` and `resources/read` takes a ticket when it arrives (stdio: in the transport's `receive`, `server::Ticketed`; HTTP: in the guard middleware, before rmcp sees the request) and holds its turn for the whole call, so calls are fully serialised in arrival order even when a client pipelines them (fixes ADR-21's consequence "may be answered out of order"). A cancelled or dropped call releases its place. `initialize`, `tools/list` and `resources/list` take no ticket.
  - **Tools (21):** `get_app_status`, `list_documents`, `get_document_info`, `create_document`, `select_document`, `get_palette`, `set_palette_color`, `draw_pixel`, `draw_line`, `draw_rectangle`, `draw_ellipse`, `fill_area`, `import_image`, `undo`, `redo`, `save_project`, `export_image`, `get_preview`, `open_picture`, `execute_command`, `get_pixels`. Arguments are strict (`deny_unknown_fields`, an unknown argument is `INVALID_ARGUMENT`). Annotations: read-only, destructive (import_image, open_picture, save_project, export_image) and idempotent hints; `openWorldHint` false.
  - **Results:** every result is a JSON object with `success`, and `document_id` and `revision` where a document is involved; it is the structured content and also the text block (clients that ignore structured content still get it). Errors are `{success: false, code, message}` with `isError: true` and stable codes (`INVALID_ARGUMENT`, `PALETTE_RANGE_INVALID`, `HARDWARE_LIMIT`, `UNSUPPORTED_MODE`, `DOCUMENT_NOT_FOUND`, `REVISION_CONFLICT`, `NOTHING_TO_UNDO`/`NOTHING_TO_REDO`, `PERMISSION_DENIED`, `FILE_ACCESS_OFF`, `PATH_NOT_ALLOWED`, `FILE_EXISTS`, `OVERWRITE_DECLINED`, `FILE_NOT_FOUND`, `DIR_NOT_FOUND`, `NOT_A_REGULAR_FILE`, `INVALID_FILE`, `UNSUPPORTED_FILE_TYPE`, `IO_ERROR`, `APP_NOT_RUNNING`, `APP_CONNECTION_LOST`, `APP_BUSY`, `APP_UNAVAILABLE`, `INTERNAL_ERROR`). An unknown tool is a JSON-RPC `invalid_params` error, not a result. `get_preview` returns the PNG image block first, then the JSON.
  - **Documents:** the picture and the spare page have the ids `page1` and `page2`; an id follows its page across Spare > Swap, so "page1" always means the same page. `select_document` swaps (like Picture > Spare > Swap); selecting the active page changes nothing (idempotent). Tools work on the active page; `get_document_info` accepts either id.
  - **create_document:**
    - Size and mode: an explicit `resolution`/`video`/`interlace` wins; otherwise a size that is exactly a standard screen gets that mode, else the first mode whose screen holds the size in the order Low Res, High Res, SuperHiRes, non-laced before laced, PAL before NTSC, with a custom screen of exactly the size (so 320×240 is PAL:Low Res with a custom 320×240 screen, and the result notes it). Presets `ntsc_lores`, `pal_lores`, `pixelart_320x240`, `ntsc_hires`, `pal_hires`, `ntsc_interlace`, `pal_interlace`.
    - Hardware limits are refused with a message that says why and what works: OCS High Res with 32 colours gives `PALETTE_RANGE_INVALID` "OCS PAL:High Res shows at most 16 colours at once, not 32 … use 16 colours, Low Res (32 colours) or AGA (256 colours)". Nothing is reduced silently.
    - It runs the engine's `SetFormat` (undoable, `undoable: true`) when the chipset stays and the document has one frame. `SetFormat` has no chipset field and this part does not add one: a chipset change (or a multi-frame document) makes a blank document and replaces the picture (`replace_picture`, not undoable, `undoable: false` and a note in the result). The integration step may move this to a chipset-aware `SetFormat` (ADR-46).
  - **set_palette_color:** `#RRGGBB` (or `#RGB`, each digit doubled); on OCS a colour that is not 12-bit (each channel a multiple of 0x11) is refused with `HARDWARE_LIMIT`, naming the nearest 12-bit colour, instead of rounding it.
  - **Drawing:** `draw_*` and `fill_area` take a palette index (checked against the palette size) and draw with a 1-pixel brush through the engine's `Shape`/`Stroke`/`FloodFill` commands, one undo step each. `execute_command` runs any raw `dpx-core` command with optional `expected_revision` and `dry_run`.
  - **import_image:** a path in an approved directory or base64 data (a `data:` URL is accepted), at most 12 MiB of data and 64 Mi pixels (`MAX_IMPORT_PIXELS`); PNG (indexed or true colour) or JPEG only. Options are ADR-42's (`position` centre/top_left, `palette` new/current, `colors`, `dither` none/floyd_steinberg/ordered), through `dpx_core::import`. Targets: `picture` (replaces the page like Load, not undoable), `spare` (the spare page in the picture's format and palette) and `brush` (the picture's palette, its own size, transparent colour 0 when the source has transparency). The conversion runs outside the owner thread; a change of the document meanwhile gives `REVISION_CONFLICT` instead of a picture made for an older palette. "A change" is another revision, another shown page, or another document: every `dpx_core::Engine` gets a process-wide number when it is made (`Engine::id`, new, additive), so a picture the user loaded meanwhile (a new engine, also at revision 0) is told apart from the one the conversion was made for.
  - **Files:** only in approved directories (ADR-24, `FileAccess`). `save_project` writes `.dpxproj` only (headless: with the spare page and project extras; the GUI: what Picture > Save writes, part 2) and marks the page saved, but only if the shown page is still the same document (slot and `Engine::id`; otherwise the result has a note and the new picture keeps its own name); `export_image` writes IFF ILBM (`.iff/.ilbm/.lbm`), IFF ANIM (`.anim`) or indexed PNG, chosen by the extension or `format` (a mismatch is `INVALID_ARGUMENT`), validated against the chipset's limits. An existing file needs `overwrite: true`; the overwrite setting then either allows it or asks the user through `Workspace::ask` (headless: "no", `OVERWRITE_DECLINED`). `open_picture` opens ILBM, ANIM, indexed PNG or a `.dpxproj` (with its spare page); true-colour PNG and JPEG are refused with a pointer to `import_image`.
  - **One picture read:** `get_preview`, `get_pixels`, `export_image` and the resources read the page through `tools::visible_picture` only, so the integration step can return the visible layer composite there (ADR-44).
  - **Resources:** `dpx://document/info` (JSON, as `get_document_info`), `dpx://document/palette` (JSON) and `dpx://document/preview.png` (base64 PNG blob); the server announces the resources capability. No subscriptions.
  - **Permissions and activity (`dpx_mcp::state`):** `Settings { read, edit, overwrite: Allowed|Ask, access }` behind an `Arc<ServerState>` the GUI can change while the server runs; a refused call says "… is turned off for AI clients (Prefs > AI & MCP)". `Activity` counts requests and tool calls and keeps the last request time and the client's name (from `initialize`), for the GUI's status display, and (part 2) the activity log. Headless modes allow read, edit and overwrite. Part 2 makes reading the gate for every tool but `get_app_status`.
  - **HTTP server (`dpx_mcp::http`):** rmcp's Streamable HTTP service on axum 0.8 (features `tokio`, `http1` only), bound to `127.0.0.1` only, path `/mcp`, default port 8765, else the next 10 ports, else any free port (`--port 0`: any). Stateless (`NeverSessionManager`, no `Mcp-Session-Id`), JSON responses (no SSE stream). It runs on its own thread with its own tokio runtime and stops on a `CancellationToken` (`HttpServer::stop` waits at most 3 s and removes the endpoint file; `Drop` does the same). A guard middleware checks, in this order: `Host` must be `127.0.0.1:<port>` or `localhost:<port>` (else 403; against DNS rebinding); any `Origin` header is 403 (browsers send it, local MCP clients do not); `Authorization: Bearer <token>` compared in constant time over the whole token (else 401 with `WWW-Authenticate: Bearer`); a body announced above 16 MiB is 413 before it is read, and a body read beyond 16 MiB too. rmcp's own Host/Origin checks are on as well.
  - **Token and discovery:** the token is 32 random bytes (`getrandom`) as 64 hex digits, new for each start of the headless HTTP mode (the GUI keeps one, part 2), or `DPX_MCP_TOKEN` (at least 16 visible ASCII characters) for the headless HTTP mode. The server writes `<config dir>/mcp-endpoint.json` `{version: 1, port, token, pid, app_path, url}` atomically (temporary file + rename) with mode 0600 on Unix, and removes it on stop only if it still names this process and port. The token in the endpoint file is a second one made for that start only, accepted besides the configured one and replaced with it by `set_token`: a file left behind by a crash names no token that still works. Before writing the file the server takes an exclusive lock on `<config dir>/mcp-endpoint.lock` (`std::fs::File::try_lock`, 0600) and keeps it until the file is removed; a second server for the same directory fails to start ("another DeluxePainter is already serving MCP clients"). The OS releases the lock when the process ends, so a crash leaves no stale lock and a reused process id fools nothing. `<config dir>/mcp-app.json` `{version, app_path, args, enabled}` (default args `["--mcp"]`) stays when the app stops: it tells the bridge what to launch and, with `enabled`, whether it may (a record without `enabled` counts as off). The config directory is the one `settings.json` uses (`DPX_CONFIG_DIR`, else `~/Library/Application Support/DeluxePainter` on macOS, `%APPDATA%\DeluxePainter` on Windows, `$XDG_CONFIG_HOME` or `~/.config` + `/DeluxePainter` elsewhere); it lives in `dpx_mcp::paths` and the app's `config::default_dir` calls it, with a test that both agree.
  - **CLI:** `deluxepainter mcp [--allow-dir DIR]...` (stdio, as before, now with the new tools and arrival order); `deluxepainter mcp --http [--port N] [--allow-dir DIR]...` (the headless HTTP server; it prints the URL and the endpoint file's path on stderr, never the token, and stops on Ctrl-C or SIGTERM, removing the endpoint file; without a config directory it needs `DPX_MCP_TOKEN`, else it refuses to start because no client could learn the token); `deluxepainter mcp-bridge` and the separate binary `dpx-mcp-bridge` (no arguments).
  - **Bridge (`dpx_mcp::bridge`):** a stdio MCP server for clients that only launch processes. It answers `initialize`, `tools/list` and `resources/list` itself from the same definitions (so a client sees the tools while the app is not running), and forwards `tools/call` and `resources/read` with rmcp's Streamable HTTP client to `127.0.0.1` only, with the token from the endpoint file. It re-reads the endpoint file whenever it (re)connects and reuses its connection while the file is unchanged. It trusts the file only while its server holds `mcp-endpoint.lock` (`endpoint::read_live_endpoint`); a file nobody holds is removed (under that lock) and nothing is sent to its port. Its HTTP client is its own (`reqwest::Client` with `no_proxy()`, no redirects, no idle connections, through rmcp's `StreamableHttpClientTransport::with_client`): rmcp's default client takes `HTTP_PROXY`/`ALL_PROXY` from the environment and would send the token through a proxy. With no reachable server: a running GUI (`mcp-app.lock` held, part 2) is never launched again: with `enabled` false the result is `APP_UNAVAILABLE` "MCP control is off in DeluxePainter. …", with it true the bridge waits up to 3 s (`STARTING_WAIT`) for its server, then `APP_UNAVAILABLE` "DeluxePainter is running, but its MCP server does not answer. …"; with no running GUI and `enabled` true it launches the app named in `mcp-app.json` and waits up to 20 s for a live endpoint; with `enabled` false it is `APP_NOT_RUNNING` "DeluxePainter is not running, and MCP control was turned off in it, so it is not started. …"; without a record `APP_NOT_RUNNING` "DeluxePainter is not running. Start it and turn on Prefs > AI & MCP." A read-only call is retried once after a lost connection; a changing call is not (it may have run) and gives `APP_CONNECTION_LOST`. The app sees the client as "<client name> via deluxepainter-bridge". The bridge keeps arrival order itself (one ticket per call) and stdout carries protocol only. `apps/dpx-mcp-bridge` is a small crate without eframe, so a client config can point at a binary that starts fast.
  - **Dependencies (all permissive, checked in `cargo metadata`):** direct: `reqwest` 0.13 (MIT OR Apache-2.0; added by the review fixes for the bridge's own client, `default-features = false`, the version and features rmcp already used: `Cargo.lock` gained only the dependency edge, still 504 packages), `axum` 0.8 (MIT), `getrandom` 0.3 (MIT OR Apache-2.0, already in the tree), `tokio-util` 0.7 (MIT, already in the tree), rmcp features `transport-streamable-http-server`, `client`, `transport-streamable-http-client-reqwest` (rmcp: Apache-2.0). New in `Cargo.lock`: axum, axum-core, http-body, http-body-util, hyper, hyper-util, tokio-stream, tower, tower-http, tower-layer, tower-service, try-lock, want (MIT); matchit (MIT AND BSD-3-Clause); sync_wrapper (Apache-2.0); chacha20, http, httparse, httpdate, ipnet, mime, rand, rand_core, reqwest, sse-stream, wasm-streams (MIT OR Apache-2.0). No ISC-only crate was added.
- Decision, part 2 (the running GUI, `apps/deluxepainter/src/mcp.rs`):
  - **The GUI workspace:** `GuiWorkspace(&mut PainterApp)` implements `Workspace` for one job; `PainterApp` owns the `JobQueue` (`mcp::Host`). Jobs run in `App::logic`, which eframe calls before every `ui` pass and, while the window is hidden, alone (eframe repaints a hidden window every 100 ms), so no requester's branch of the pass can starve them and calls are served while the window is minimised. The ui-loop helper `tests::ui_pass` runs `logic` before `ui`, as eframe does. The server's wake callback is the window's cloned `egui::Context::request_repaint`. One pass runs every queued job; changes set `dirty` and the same pass draws them.
  - **Job kinds and busy rules:** every job carries its call's kind: `Read`, `Edit` (every job of a tool that needs the edit permission, `ToolCtx::editing`) or `Ask`. Reading jobs always run. While any modal is open (`modal_open`: every requester, notes, the choice requester, Show Page, playback, the Control Panel, the Move preview; part 3: except Prefs > AI & MCP) `Edit` and `Ask` jobs are refused with `EDITOR_BUSY` "a requester is open in DeluxePainter, so nothing was changed; reading still works. Try again after the user has closed it." While a mouse button that started a gesture on the picture is held (`gesture_held`: a stroke or shape whose button is down, a brush being moved) they are held back, at most `HOLD_LIMIT` = 10 s after they were queued, then refused with `EDITOR_BUSY` ("the user has been painting …"). A held job keeps its place; calls run one at a time in arrival order anyway, so a read never waits behind a held change.
  - **A change is a menu command:** it takes the path of `run_action` → `run`: Stencil > Paint ends (as for every other menu item, ADR-39), a gesture that no button holds (a polygon's corners, a curve's bend, typed text) is committed first as its own undo step (`finish_stroke`), CLR on a fixed background restores it (ADR-15), the area stencil wraps strokes, shapes, fills and CLR (ADR-39), and frame commands move the area stencil with their frame (`execute_request`, as `execute_frames`). The colour stencil (Effect > Stencil) is not applied: it belongs to the painting tools' gestures and menu commands do not use it either; `execute_command` can give a command its own `stencil`. Each call is one undo step of the shown page, so U and Shift+U take it back like any other; MCP `undo`/`redo` step the shown page's history (after ending Stencil > Paint, so they never undo a mask stroke). Afterwards the colours and the scroll position are clamped and the screen is redrawn. A dry run changes nothing and ends nothing.
  - **Replacing the picture** (`create_document` with another chipset, `open_picture`, `import_image` to the picture) works as Picture > Load (`set_picture`): a new engine (not undoable), the page grown to the screen (`page_at_least_screen`), cycling reset, the palette to restore. A picture not read from a file is unsaved (and autosaved, ADR-34); one read from a file is clean. A new picture without file extras gets the default colour ranges.
  - **Documents:** `page1` and `page2` are the picture and `MenuData.spare`. `Host::swapped` flips with every Picture > Spare > Swap, the `j` key included, so an id stays with its page. `spare()` shows the spare as a swap would (`take_spare`'s rules, without changing it); `set_spare_page` is one undo step on the spare, as Copy to Spare; `select_document` is Swap. `import_image` to the brush sets the custom brush as a pick-up does (Matte mode, Brush > Restore keeps it, an AnimBrush ends).
  - **Files through the app's own code:** `save_project` and `export_image` encode through the server state's `Codec` (`dpx_mcp::codec`): headless `BuiltinCodec` (`pictures.rs`), the GUI `AppCodec`, which calls `files::encode_as` (new; `files::encode_document` now calls it). The bytes are what Picture > Save / Export write: colour ranges (CRNG), grab point and transparent colour; a GUI project has no spare page, as Picture > Save. The tools still resolve every path with `FileAccess`, check an export's hardware limits before any encoder runs (`validate_hardware`, nothing reduced silently) and write with `FileAccess::write_file`. `save_project` sets the picture's file name and marks it clean (also for the recovery slot, ADR-34) if no change came in between.
  - **Overwrite question:** `overwrite: true` on an existing file with "overwrite without asking" off asks through `Workspace::ask`: the choice requester (ADR-34) titled "Replace File?" with "Claude wants to replace NAME. Replace?" ("Claude" for a client whose name contains "claude", else the client's own name, else "An AI client") and the buttons Replace and Keep. Return and Esc mean Keep; only a click replaces the file, because the requester appears without the user asking for it and a key meant for the picture must not replace a file. The call waits. Without an answer within `ASK_TIMEOUT` (45 s) the requester closes and the call fails with `OVERWRITE_DECLINED` ("nobody answered within 45 s; the existing file … was kept"). With another requester open the question is not shown (`EDITOR_BUSY`); one that replaces it (Quit) fails the call with `EDITOR_BUSY`. `Workspace::ask` now answers `Result<bool, ToolError>` (the headless one `Ok(false)`). Without `overwrite: true` an existing file stays `FILE_EXISTS` and nobody is asked: the client has to ask to replace, then the user has to agree (owner's spec §7.4 and §7.6).
  - **Permissions:** reading off refuses every tool but `get_app_status`, the changing ones too (their results describe the document); changing needs both permissions. Changes of the settings apply to the next call.
  - **Settings section `mcp`** (settings.json, ADR-33, no version bump): `enabled` (false), `port` (8765), `allow_read` (true), `allow_edit` (true), `overwrite_without_asking` (false), `approved_dirs` (default `[<Pictures>/DeluxePainter]`; Pictures is `~/Pictures` on macOS, `%USERPROFILE%\Pictures` on Windows, `$XDG_PICTURES_DIR` or `~/Pictures` elsewhere; the XDG `user-dirs.dirs` file is not read). A missing key keeps its default; an explicit empty list turns file access off. The default directory is created when the server starts and it is missing; another approved directory that does not exist is left out (`Host::missing_dirs`) instead of failing the start. Permission and directory changes apply to the running server at once; a new port restarts it.
  - **`--mcp`** turns the server on for one session (not saved); it is the flag the bridge launches the app with (`mcp-app.json`). **One GUI per config directory answers MCP clients:** the first GUI holds `<config dir>/mcp-app.lock` while it runs (`mcp::claim_instance`, taken in `main` before the window opens). A `--mcp` start while another GUI holds it ends at once with "DeluxePainter is already running: --mcp does not start a second one …" (stderr) and opens no window; a plain second start (the user's) runs without the lock.
  - **Lifecycle:** the server starts in the first pass while enabled (or with `--mcp`) and stops when it is turned off and in `on_exit`; queued calls and an open question then fail with `APP_UNAVAILABLE`, and the endpoint file is removed. A start that fails (`Status::Failed`, e.g. the token file cannot be written) is tried again after the settings change or after MCP control was turned off and on again: Off forgets the failure, and the status says "Off", not the old error (`Status::Failed` only while MCP control is on). The token is kept in `<config dir>/mcp-token` (0600 on Unix, replaced if damaged), so a client configured once reconnects after a restart; a token file found readable by group or others (Unix) may have given the token away and is replaced by a new private one, not only tightened. `mcp_revoke` writes a new token and swaps it into the running server (`HttpServer::set_token`; the old token and the endpoint file's old token get 401 at once), and the endpoint file gets a new token of its own. **Off sticks:** the app keeps `mcp-app.json` equal to MCP control: when it is turned on the app writes this executable, `--mcp` and `enabled: true`; when it is turned off (the Off radio, Disconnect > Turn off, the end of a `--mcp` session) it writes `enabled: false` over an existing record (an app whose MCP control was never on leaves no file); on exit it writes the saved setting (a `--mcp` session is not saved). With the lock above, the bridge therefore never starts the app while MCP control is off and never starts a second one (before the review fixes it started `<exe> --mcp` whenever no server answered, a second window with MCP on included). Without a config directory the token is random per start and no files are written; `--no-settings` still keeps these files in the config directory.
  - **Activity log:** `ServerState::activity()` keeps the last 50 calls (`LogEntry`: wall-clock time, tool, ok, the error code, and what the call did, e.g. `draw_rectangle 10,20 20x10 colour 5 filled` from the workspace's log line, or the error message) with a serial number for redraws. `mcp::Host` exposes `status`, `activity`, `log`, `missing_dirs` and `token` (tests only; the token is never drawn or put in a command) for part 3.
  - **Snapshot flags:** `--mcp-calls FILE.json` runs MCP tool calls on a GUI workspace before the snapshot (each result on stderr); `--mcp-question NAME` shows the overwrite question. Screenshots: `docs/design/screenshots/wave8-mcp-gui-calls.png` (with its `.json`) and `wave8-mcp-replace-question.png`.
  - **Dependencies:** none added in part 2 (`Cargo.lock` unchanged); the app reaches rmcp's result type through `dpx_mcp::CallToolResult`.
- Decision, part 3 (Prefs > AI & MCP.., the connect flows, the extension; `crates/dpx-ui/src/mcp_requester.rs`, `apps/deluxepainter/src/mcp_prefs.rs`, `apps/deluxepainter/src/connect.rs`, `crates/dpx-mcp/src/bundle.rs`, `xtask/`):
  - **Transport, in short (parts 1 and 2):** the running GUI serves MCP Streamable HTTP on `127.0.0.1`, and a stdio bridge (`dpx-mcp-bridge`, also `deluxepainter mcp-bridge`) is the process the clients launch. Clients launch stdio servers themselves and cannot be pointed at the running app; Claude Desktop takes local servers only as stdio commands or `.mcpb` bundles (a localhost URL in its config is reported as refused by secondary sources, unverified); the bridge works whether the app runs or not (it answers `initialize` and the lists itself and starts the app through `mcp-app.json`). This supersedes ADR-5's local socket / named pipe plan: one protocol end to end, rmcp's own server and client, no `interprocess` dependency, and the HTTP endpoint can also be used directly.
  - **Security model, in short:** the server listens on `127.0.0.1` only and only while MCP control is on (off by default). Every request needs `Host` `127.0.0.1:<port>`/`localhost:<port>` (DNS rebinding) and no `Origin` (browsers), and `Authorization: Bearer` with the 32-byte random token, compared in constant time. The token is kept in `<config dir>/mcp-token`, and the endpoint file holds a second token made for that start of the server, both 0600 on Unix (Windows: only the profile directory's ACL, unverified); the bridge sends a token only to a server that holds the endpoint lock, through no proxy, so a port taken over after a crash (any local user can listen on a port above 1024) gets nothing, and a stale endpoint file names a dead token. The token never appears on screen, in a command line, the clipboard, a project or `settings.json`: the bridge reads the endpoint file. Reading and changing are separate permissions applied to the next call; file tools only touch approved directories; replacing a file needs `overwrite: true` and the user's click (or "Overwrite files without asking"). No tool runs a shell command.   - A release has to ship the `.mcpb` next to the executable (or in the macOS app bundle's `Resources`) for Connect Claude Desktop to work; CI makes it, packaging is not done yet. Signing and notarizing the bridge and an icon are open (owner's call for branding).
  - The README's "connect in two minutes" guide is left to the integration step (this strand does not edit README.md).
  - An AI change waits for the user's stroke and never lands under an open requester; a client sees `EDITOR_BUSY` and has to try again.
  - MCP changes are undo steps of the picture like the user's own, so the user's U can undo Claude's last change and Claude's `undo` the user's last stroke.
  - hyper/axum/reqwest enter the app binary; the bridge binary carries them too but not eframe.
  - Anyone who can read the user's config directory can read the token and call the app; that is the same trust boundary as `settings.json` and the user's files.
