# ADR-24: MCP tools and file access

- Status: accepted (Phase 1/2, 2026-11-10); extends ADR-21 and implements the file-access rule of ADR-5.
- Context: the spike (ADR-21) could create a document and describe it. An agent needs to paint, look at the result and save it, and the approved-directory rule had nothing to enforce until a file tool existed.
- Decision:
  - `deluxepainter mcp [--allow-dir DIR]...` (also `--allow-dir=DIR`). Every directory must exist (canonicalised at start; otherwise the process exits with an error on stderr, stdout stays empty). No `--allow-dir`: every file tool fails with `FILE_ACCESS_OFF`. Argument parsing lives in `dpx_mcp::run_cli`; `main.rs` only forwards the arguments.
  - Path rules (`access.rs`): a relative path starts at the first approved directory. Reads canonicalise the path (symlinks followed) and require it to lie inside an approved directory and be a regular file. Writes canonicalise the parent, require it inside, refuse a symlink or non-regular target, and refuse an existing file unless `overwrite=true` (new files are created exclusively; replacing goes through a temp file and rename). Missing paths outside the approved directories report `PATH_NOT_ALLOWED`, not "not found", so nothing is revealed. Codes: `FILE_ACCESS_OFF`, `PATH_NOT_ALLOWED`, `FILE_NOT_FOUND`, `DIR_NOT_FOUND`, `FILE_EXISTS`, `NOT_A_REGULAR_FILE`, `IO_ERROR`, `UNSUPPORTED_FILE_TYPE`, `INVALID_FILE`, `HARDWARE_LIMIT`. Command errors keep the dpx-core code (`INVALID_ARGUMENT`, `REVISION_CONFLICT`, ...); every failure is an `isError` result reading `CODE: message`.
  - Tools: `execute_command` (a serde `Command` as JSON in `command`, optional `expected_revision`, `dry_run`; returns revision, `changed_rect`, palette/format flags, can_undo/can_redo), `undo`, `redo`, `get_palette` (`#RRGGBB` strings), `get_pixels` (clipped rect, at most 65 536 pixels; `rows` of index arrays by default, `base64` raw bytes on request), `render_png` (page or rect, integer scale 1..8, at most 4 194 304 output pixels, RGB PNG as MCP image content plus a text block with the rect and size; pixel aspect is not corrected), `open_picture`, `save_picture`. Handlers only call `Engine`; no pixel logic in `dpx-mcp` beyond palette lookup and scaling for the image.
  - `open_picture` reads indexed IFF ILBM and indexed PNG (64 MiB cap) and replaces the document with a fresh engine (revision 0, no undo). Display mode, screen size and page growth follow the app's `open_picture` rules (ADR-10, ADR-11). True-colour PNG and JPEG are refused with `UNSUPPORTED_FILE_TYPE`: the colour reduction (ADR-9) lives in the app crate, which depends on `dpx-mcp`. The few lines of indexed open/encode glue are therefore duplicated in `dpx-mcp/src/pictures.rs`; moving `files.rs` into a library crate would remove that.
  - `save_picture` writes `.iff/.ilbm/.lbm` (ILBM with the mode's CAMG, aspect and screen size) or `.png` (indexed); other extensions are refused (the GUI defaults unknown extensions to ILBM). Before writing it validates the target's rules and fails with `HARDWARE_LIMIT` instead of reducing anything: mode available on the chipset, palette size within the mode's maximum, page within the target's page limits, OCS palette entries representable in 12 bits, pixels inside the palette.
  - The headless engine has no colour ranges or transparent colour; `open_picture` reports dropped ranges, masks and transparency in `notes`, and ranges are not written back.
- Verified (macOS, local): unit tests for path rules (traversal with `..`, symlink escape for files and directories, absolute paths outside, missing directories, overwrite, no temp leftovers), the tools (execute/dry-run/conflict/undo/redo, pixel cap and clipping, PNG render pixel check, ILBM/PNG round trip, hardware limit errors); stdio integration tests (new_document, execute_command, render_png decoded and a pixel checked, undo, get_pixels, save/open, refused paths, file access off, bad `--allow-dir`); a manual piped JSON-RPC session; stdout carries protocol lines only.
- Not verified: Windows (symlink tests are unix-only; path canonicalisation yields `\\?\` paths there), Linux, real MCP clients (image content rendering); a symlink or directory swapped between the path check and the write (race); case-insensitive file systems with a differently cased approved directory beyond what `canonicalize` normalises.
- Consequences: `dpx-mcp` now depends on `dpx-formats`, `dpx-iff`, `png` and `base64` (already in the tree via rmcp; MIT/Apache-2.0). rmcp still handles requests concurrently, so a client that pipelines dependent calls (a command and its `undo`) without waiting for the reply can see them executed out of order; clients should await each result.

- Review fixes (fix/mcp): paths are checked lexically (no `..` escape, same drive/UNC prefix as an approved dir) before any canonicalize or file system access; missing-file errors only appear once the nearest existing ancestor is confirmed inside an approved directory; overwrite temp files have per-call unique names and only a temp file this call created is removed; argument deserialisation errors are reported as `INVALID_ARGUMENT: ...` results; EHB opens as 64 colours and HAM is refused (ADR-26).
