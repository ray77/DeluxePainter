# ADR-41: Tooltips naming the tools

- Status: accepted (2026-11-11; the owner asked for English tooltips naming the tools; the details below were decided without the owner)
- Context:
  - The owner asked for "an English tooltip with the name of the tools".
  - DeluxePaint IV AGA has no tooltips: the toolbox shows icons only, and the names and keys are in the manual. This is a DeluxePainter addition, like the off-page pattern (ADR-13).
  - The visible interface is our own software-rendered pixel UI (ADR-3); no egui widgets. egui runs a pass only on input or when asked for one, so a tooltip that appears after a delay must ask for its own pass.
  - The keys that select tools and run panel buttons are spread over several handlers (`tools.rs` tool keys, `menu_actions.rs`, `anim.rs`, `anim_control.rs`, `main.rs` for `u`). A key printed in a tooltip must be one that really does the same on the paint screen.
  - Two modes take keys before those handlers see them, while the buttons keep working: Effect ▸ Perspective (ADR-37; `perspective_keys` runs first and takes the main-row digits with and without Shift and the characters of its keypad table, `<` and `>` among them) and the Text tool while it types (every key goes into the text).
- Decision:
  - **Targets:** the 18 toolbox tool buttons and, while it is shown, the buttons of the Animation Control Panel (ADR-38). Split buttons (Continuous Freehand, Rectangle, Circle, Ellipse, Polygon) name the half under the pointer: the upper-left half the outline / continuous variant, the lower-right half the filled one; the text changes at once when the pointer crosses the diagonal. No tooltips for the built-in brushes, palette cells, colour indicator, title bar, page, the panel's slider, requesters or menus.
  - **Text:** one line, the English name, two spaces, then the paint-screen key that does the same, if there is one. Letters as typed (a capital means Shift with the letter), modifiers as `Shift+1`, `Ctrl+1`, `Alt+=` (Alt is Option on macOS). The tool names are `Tool::name()`; the split halves and the panel buttons are named in our own words after what they do (no manual text):

    | Button | Tooltip |
    |---|---|
    | Dotted Freehand | `Dotted Freehand  s` |
    | Continuous Freehand, upper-left / lower-right | `Continuous Freehand  d` / `Filled Freehand  D` |
    | Line | `Straight Line  v` |
    | Curve | `Curve  q` |
    | Fill | `Fill  f` |
    | Airbrush | `Airbrush` |
    | Rectangle | `Rectangle  r` / `Filled Rectangle  R` |
    | Circle | `Circle  c` / `Filled Circle  C` |
    | Ellipse | `Ellipse  e` / `Filled Ellipse  E` |
    | Polygon | `Polygon` / `Filled Polygon` |
    | Brush Selector | `Brush Selector  b` |
    | Text | `Text  t` |
    | Grid | `Grid  g` |
    | Symmetry | `Symmetry  /` |
    | Magnify | `Magnify  m` |
    | Zoom | `Zoom  >` |
    | UNDO | `Undo  u` |
    | CLR | `Clear  K` |
    | Panel: First / Last Frame | `First Frame  Shift+1` / `Last Frame  Shift+2` |
    | Panel: loop / play once backward | `Loop Backward  Shift+4` / `Play Once Backward  Shift+5` |
    | Panel: previous / next | `Previous Frame  1` / `Next Frame  2` |

  - **Keys follow the keyboard's mode** (`dpx_ui::tooltip::KeyMode`): a tooltip names a key only while it does the button's job. In perspective mode the digits (with and without Shift) and `>` belong to the mode, so Zoom, First/Last Frame, the playback buttons, Previous/Next Frame and Repeat Go To show their names alone (e.g. `Zoom`, `Previous Frame`); the letters, `/`, `Ctrl+1`..`Ctrl+4` and `Alt+=` stay. While the Text tool types, every tooltip shows the name alone. The text changes in the pass that changes the mode (Return into or out of perspective mode, Esc ending the text), under a resting pointer too.

  - **When:** after the pointer has rested 0.5 s on the same target (tool and half, or panel button); moving on the same target does not start the delay again. Once a tooltip shows, moving straight onto another target shows that one at once; leaving all targets (page, palette, brushes, the 1-pixel gaps between buttons, the slider, outside the window) hides it, and the next one waits the full delay again. Hidden, and the delay starts again afterwards: on any mouse button press and while a button is held; while the menu strip is shown; while a requester, note, file requester, Show Page, playback or the Move preview is open (`PainterApp::modal_open`; Play Once ends by itself at its last frame, with no input that would bring the next pass, so the upload that finds the modal gone asks egui for one more pass and the hover branch starts the delay under the resting pointer); a tool tooltip while the toolbox is hidden (F10) and a panel tooltip while the panel is off (their buttons are not hit then, and `Tooltip::layout` draws no box for a button that is not shown).
  - **Repaints:** while the pointer rests and the tooltip is not shown yet, the pass asks egui for one more pass when the delay is over (`request_repaint_after(remaining)`), so an idle window shows it. Once it shows, it asks for nothing (no repaint loop). When the menu strip or a modal closes, one pass is asked for (`request_repaint`, once per close). The screen is redrawn (`dirty`) only when the shown tooltip (its button or its text) changes.
  - **Look:** drawn in UI (LoRes) pixels by `Screen::draw_ui`, last, over everything, so it scales with the interface in HiRes and laced screens. Everything `compose_screen` adds after the interface (the Grid/Symmetry/Magnify toggle marks, the unselected built-in brush) stays inside the toolbox, which no box covers; the Text tool's cursor is drawn into the page before the interface (below). A box filled with the face pen, a 1-pixel dark border, square corners, the text in the dark pen with the built-in font, 2 blank columns left and right of the text, 12 pixels high (border, a blank row, the 8 font rows, a blank row, border: one free row above the capitals and below the descenders, as compact as the 11-pixel title bar).
  - **Place:** toolbox buttons: the box lies left of the toolbox, its right edge 2 pixels left of the toolbox (two free columns), its top at the top of the hovered button. Panel buttons: above the panel (two free rows), its left edge at the button's left edge, pushed left so that it ends at the panel's right end (it never covers the toolbox). Always clamped inside the screen; a text wider than the screen would be cut (none is). It never covers the hovered button.
  - **Code:** `crates/dpx-ui/src/tooltip.rs` holds the texts (`for_tool`, `for_panel_button`, `tool_key`, `panel_key`, `TooltipTarget::text_in` with a `KeyMode`), `TooltipTarget::of_hit`, `Tooltip::layout` and `Tooltip::draw`; `UiState::tooltip` (default `None`) is what is drawn, with the `KeyMode` its text was made for; `Screen::tool_button` gives a tool's button rectangle. `apps/deluxepainter/src/tooltip.rs` holds the state machine (target, since when, shown, and whether the last upload was blocked by the menu strip or a modal): `tooltip_hover` is fed from the hover branch of `PainterApp::ui` with the hit under the pointer and egui's time, `tooltip_guard` runs at the start of every upload, clears it while the menu strip or a modal is open (every path of `ui()` ends in an upload, so a key that opens a requester or starts playback in the same pass also hides the tooltip before it is drawn, and the modal paths never feed the hover state), asks for the one pass after a modal closes and brings the text up to the key mode (`tooltip_keys`: typing, perspective mode, else the paint screen).
  - **Text cursor under the interface:** `compose_screen` draws the Text tool's cursor into the shown page (the normal half while magnifying) before the interface is drawn over it, instead of over the finished screen. The tooltip, the toolbox, the title bar, the panel, menus and requesters now cover the cursor as they cover the typed text it follows; before, a cursor under them showed through.
  - **Control Panel frame commands:** the panel's Add Frame, Delete Frame and frame steps go through `execute_frames` (ADR-39) like the keys and menus, so the area stencil and Stencil ▸ Paint follow their picture when the panel adds or deletes a frame. Before, the panel (ADR-38) ran them on the engine directly, and an area stencil on a later frame stayed at its old index (on another picture) after Add Frame or Delete Frame from the panel, while `Alt+=` moved it along.
  - **One source for the keys:** the keys exist only in the `dpx-ui` text table, and `KeyMode::keeps` says which of them a mode leaves out. The app tests, on the paint screen, in perspective mode and while typing, rest the pointer on every target until its tooltip shows, press the key of the table (as egui-winit sends it) and compare the result with a click on that button (half) on a second app in the same state: a key the tooltip names must do exactly what the click does, a key it leaves out must do something else. Either drift fails a test.
  - **Snapshots:** `--hover X,Y` (UI pixels) renders the screen with the tooltip a rested pointer at X,Y shows; it combines with `--anim-panel`, `--tool`, `--frames`, `--palette` and the other snapshot options, and shows none while `--menu` or a requester option is given. It prints a note when nothing with a tooltip lies at X,Y.
- Decided without the owner:
  - Tooltips at all (the request), their English texts, the 0.5 s delay, the look and the places above.
  - `Clear  K` although `k` clears too (`menu_actions.rs`); `K` is the key of the manual's keyboard table (ADR-14). Grid is shown as `g` (`G` works too). Zoom shows `>` (zoom in, as a left click; the right click and `<` zoom out).
  - The Go To button is named "Repeat Go To" after what a left click does (the frame of the last Go To; the Go to Frame requester before any Go To and with Ctrl or the right button); Shift-3 does the same.
  - "Loop" for the forward loop button (key `4`, Anim ▸ Control ▸ Play) next to "Loop Backward".
  - Airbrush, Polygon (both halves) and Delete Frame show no key: none selects or runs them.
  - The gaps between toolbox buttons count as leaving the targets (as asked), so moving slowly from one button to the next can hide the tooltip on the 1-pixel gap and wait the delay again.
  - In perspective mode and while typing the tooltips still show, naming the button without the keys the mode takes (rather than no tooltip at all): the buttons keep working there.
  - The Text tool's cursor lies under the interface like the typed text (it no longer shows through the toolbox, title bar, menus or requesters).
  - The Control Panel's frame commands follow ADR-39 like the keys (a fix of ADR-38's panel, found because the tooltip says the button and `Alt+=` are the same).
- Verified:
  - Unit tests (`dpx-ui`): the text of every tool and both halves of every split tool, and of every panel button (exact strings, font characters only); the texts in perspective mode (Zoom and the ten digit-key panel buttons without keys, the rest with) and while typing (every target its name alone), and which keys `KeyMode::keeps`; targets from hits on both halves of every button and every panel button, none for brushes, palette, indicator, title bar, page, slider and gaps; every box inside the screen beside its button and never over it, for every target on 320×200 (the smallest UI screen), 320×256, 368×241, 368×283 and 352×272 with the toolbox shown and hidden; long texts clamped and cut with the border intact; border, square corners (the corner pixels are the border pen, the pixels inside them face) and the text exactly as the font draws it; drawn last over page, toolbox and panel (the screen with the tooltip equals the screen without it plus the box), scaled 2×2 in a laced HiRes screen; nothing drawn for a hidden toolbox or panel.
  - App tests (`apps/deluxepainter/src/tooltip.rs`) through `PainterApp::ui` with real egui pointer, key and modifier events: no tooltip before 0.5 s; the repaint delay while resting is at most the remaining time (0.5 s at first, at most 0.2 s after moving on the same button), the next idle pass shows it, and then egui asks for no pass (`Duration::MAX`), also after pointer moves on the button; the box on the composed screen; the next button, the other half of a split button and further buttons at once; a gap, a brush, the palette and the page hide it and the next button waits again; pointer gone; a left press hides it, nothing while held, the delay again after the release; a right click on Zoom; the menu strip, Picture ▸ Page Size.. picked from it (no tooltip under the requester, the delay again after Esc), `F` opening the Fill Type requester while it shows; `4` starting playback under a panel tooltip; F10 under a resting pointer, no tool tooltips without the toolbox, panel tooltips over the full-width panel, Alt-a switching the panel off; every panel button in turn (each at once), the box above the panel, none on the slider and the gap; every one of the 20 tool keys and the 16 panel keys (with and without an earlier Go To) does exactly what a click on its button does, compared on tool, toggles, zoom, page, undo/redo, frame, frame count, playback, requesters, Light Table, the area stencil's frame (one on a later frame), perspective mode and typing; in perspective mode 19 tool keys and 6 panel keys are named and do what the click does, while `>` and the 10 digit keys are left out and each does something else (turns the brush, moves the observer); while typing all 20 tool keys and 16 panel keys are left out and each types instead; Return into and out of perspective mode and Esc ending the text change the shown text in that same pass; while typing, the box on the composed screen equals the box drawn alone (the cursor bar under it), and the cursor shows again once the pointer is on the page; Play Once clicked under its tooltip, the window run only when egui asks: after it ends by itself the tooltip shows again 0.5 s later (±0.01 s) and then nothing more is asked for; Delete Frame from the panel moves an area stencil on a later frame back by one and drops one on the deleted frame, Add Frame moves it on by one; `--hover` parsing.
  - Mutation check (each piece reverted once; the counts are failing tests of `cargo test -p deluxepainter`, re-run after the review fixes): showing at once instead of after the delay failed 5 tests; no hiding on a press 1; no repaint request while resting 14; no modal check in the guard 3; no guard call before the upload 4; the next target waiting the delay again 2; moving on the same target restarting the delay 14; leaving the targets keeping it shown 4; the key mode always the paint screen 3; no pass asked for after a modal closes 1; the text brought up to the key mode only while a modal is open 1; the panel's frame commands bypassing `execute_frames` 3; the text cursor drawn over the finished screen again 1. One mutation survives: without the menu-strip check in the guard nothing fails, because the strip opens only with a right press on the title bar (which already hides the tooltip and resets the delay) and the hover branch does not run while it is shown; the check stays as a guard. A second guard check (hide when the toolbox or panel is gone) also survived in the first run and was removed, since the hit test and `Tooltip::layout` already cover it.
  - Snapshots (`--snapshot … --scale 3`, looked at): `--hover 300,48` shows "Straight Line  v" left of the toolbox at the Line button's top, two free columns before the toolbox; on a page cleared to colour 7 the 1-pixel black border and square corners show; `--tool rectangle:filled --hover 305,77` shows "Filled Rectangle  R" (also cropped at scale 8: border, corners, gap); `--anim-panel --frames 4 --hover 66,250` shows "Next Frame  2" above the panel at the button's left edge; `--light-table --hover 288,250` shows "Light Table: Spare  Ctrl+4" pushed left to end at the panel's right end, off the palette; on the 320×200 NTSC screen (`--commands` with a `set_format`) `--hover 3,183` shows "First Frame  Shift+1" at the left edge above the panel and `--hover 300,132` "Undo  u"; `--hover 100,100` on the page prints the note and shows none. Re-rendered after the review fixes (`fixed-*.png`, looked at): "Straight Line  v" and "Filled Rectangle  R" left of the toolbox at their buttons' tops; "Next Frame  2" above the panel at the button's left edge; on 320×200 "First Frame  Shift+1" at the left edge above the panel and "Undo  u" beside UNDO; on a page cleared to colour 7 at scale 8 the 1-pixel black border, square corners and the two free columns/rows to the toolbox and the panel ("Loop Backward  Shift+4" at the left edge). Snapshots start on the paint screen, so they always show the keys; the perspective and typing texts and the cursor under the box are checked by the tests only.
  - Not verified: a real pointer and keyboard in the window, a Play Once ending in the real event loop (the test runs passes only when egui asks, as an idle window does) (the owner declines remote control of the app; the tests drive `ui()` with the events egui-winit sends), the keys on non-US layouts beyond what the key handlers already document (Shift-digits are read from the physical key; `Alt+=` is Alt with the `=` or `+` key), Windows and Linux.
