# ADR-45: AI image generation, part 1: provider interface, OpenAI Images, API keys, jobs and conversion

- Status: accepted (2026-11-12; wave 8, strand "AI image generation", part 1 of 2: the core without GUI). The owner's implementation spec ("DeluxePainter – MCP-Anbindung und KI-Bildgenerierung", §1, §3.2, §4, §5.1, §7, §10 test 5 and 6) and the owner decisions for wave 8 (below) set the frame; the points under "Decided without the owner" were not asked. Part 2 adds the requester (Picture ▸ Generate..) and the provider settings (Prefs ▸ AI & MCP..); the integration step wires MCP tools and the "New layer" target.
- Context:
  - The spec wants pictures generated from a description by a real, explicitly set-up generator behind a provider interface, converted to the exact target size, colour count and chipset limits, applied with undo, never faked, with keys in the OS keychain, costs and network use stated before generating, progress and cancelling, and no blocking call on the GUI thread.
  - DeluxePaint IV has nothing like it; this is a DeluxePainter addition. Pixel logic stays in `dpx-core` (CLAUDE.md); network, keys and threads get a crate of their own so `dpx-core` keeps no dependencies but serde.
  - Research notes from the scouting pass (provider APIs, crate licences, the import pipeline) were the starting point; the OpenAI facts below were re-read from the official pages on 2026-11-12.
- Decision:
  - **Crate `dpx-imagegen`** (depends on `dpx-core`, `dpx-formats`; no GUI crate): `provider` (the trait, requests, capabilities, errors, cancel token), `size` (which size to ask for), `openai` (the first provider), `secret` (API keys), `jobs` (worker threads), `fixture` (a test pattern for tests only). `user_providers(keys, openai_config)` is the list the GUI and MCP offer: OpenAI only.
  - **`ImageGenerationProvider`** (`Send + Sync`, called on worker threads): `id`, `display_name`, `needs_network`, `cost_note` (an honest ASCII note on cost and where the prompt goes, shown before generating), `capabilities` (`SizeRule`, transparent background, most variants, seed, longest prompt), `status` (`Ready` or `NotConfigured(what is missing)`), and `generate(&GenerationRequest, &CancelToken) -> Result<Vec<RgbaImage>, GenError>`. A `GenerationRequest` carries the prompt, the provider size to ask for, the number of variants, transparent background and an optional seed; `GenerationRequest::for_page` takes the size from the page's display proportions. `Capabilities::check` refuses, before anything is sent, an empty or too long prompt, a size the provider does not make, 0 or too many variants, transparency or a seed the provider does not offer.
  - **Typed errors (`GenError`)** with stable codes for MCP: `NotConfigured` (`NOT_CONFIGURED`), `InvalidRequest` (`INVALID_REQUEST`), `Auth { status }` (`AUTH_FAILED`: HTTP 401 and 403), `RateLimited { quota_exhausted, retry_after }` (`RATE_LIMITED` / `QUOTA_EXCEEDED`: HTTP 429), `ContentPolicy` (`CONTENT_POLICY`), `Network` (`NETWORK`), `Timeout` (`TIMEOUT`), `Cancelled` (`CANCELLED`), `BadResponse` (`BAD_RESPONSE`), `Server { status }` (`SERVER_ERROR`: 5xx), `Busy { running }` (`BUSY`). `retryable()` says whether trying again unchanged may help (rate limit, network, timeout, server, busy; not quota, policy or auth). Every `Display` text is ASCII (the pixel UI's font). Messages from a service are cleaned (`clean_message`): printable ASCII only, whitespace collapsed, at most 200 characters, and any word containing `sk-` (an API key fragment, as OpenAI's 401 message quotes) replaced by `[key]`.
  - **OpenAI Images** (`OpenAiProvider`, id `openai`, "OpenAI Images"):
    - `POST https://api.openai.com/v1/images/generations` with `Authorization: Bearer <key>`, `Content-Type: application/json`, `User-Agent: DeluxePainter`, and the JSON body `model`, `prompt`, `size` ("WxH"), `quality`, `background` (`transparent` when asked, else `opaque`, so no picture comes back with an unexpected alpha channel), `output_format` `png`, `n` (variants, 1–10). The answer's `data[].b64_json` is base64-decoded and read with `dpx_formats::read_png` (64-megapixel cap, ADR-9; an indexed PNG becomes RGBA in its palette's colours). The answer is read up to 256 MB.
    - **Model:** a setting (`OpenAiConfig::model`, any 1–64 printable ASCII characters), default **`gpt-image-2.6-flare`**. Checked on 2026-11-12 (`MODELS_CHECKED`): the models page lists `gpt-image-2.6-sunburst`, `gpt-image-2.6-flare`, `gpt-image-2.5-sunburst` and `gpt-image-2.5-flare`, none deprecated; the deprecations page shuts down `gpt-image-1` (2026-10-23), `gpt-image-1.5`, `gpt-image-1-mini` and `chatgpt-image-latest` (2026-12-01), `gpt-image-2` (announced 2026-11-10, shut down 2027-02-10) and DALL·E 2/3 (2026-05-12), and names `gpt-image-2.6-sunburst` or `gpt-image-2.6-flare` as the replacement of every image model shut down from 2026-12 on. Flare is the one for "fast iteration", Sunburst for "detailed visual work". The model page of `gpt-image-2.6-flare` lists only the undated snapshot of the same name, the generations and edits endpoints, and $5 / $8 / $30 per million text-input / image-input / image-output tokens; its rate limits depend on the account.
    - **Quality:** a setting, default `medium` (`low`, `medium`, `high`, `auto`; the API also takes `xhigh` and `max` for these models, not offered yet).
    - **Sizes** (`CustomSizes::OPENAI`, from the image generation guide): width and height multiples of 16, at most 3:1, 655,360 to 8,294,400 pixels, sides up to 3840 (above 2560×1440 "experimental"). `SizeRule::choose` asks for the long side 1024 (the side of OpenAI's standard sizes) with the nearest multiple of 16 as the short side, larger only when the pixel minimum needs it; if a long side up to a quarter larger gives the proportions exactly, that one (nothing to crop then). Proportions beyond 3:1 are asked at 3:1 and cropped. Results for the Amiga pages (page × pixel shape): 320×240 → 1024×768; 320×200, 640×200 HiRes, 640×400 → 1024×640; 320×256, 640×256 HiRes, 640×512, 320×512 LoRes laced, 1280×256 SuperHiRes → 1040×832; 368×283 overscan → 1024×784 (cropped by 0.2 %); 3:1 → 1440×480.
    - **Errors:** OpenAI's `{"error": {"message", "type", "code"}}`: 401/403 → `Auth`; 429 → `RateLimited`, `quota_exhausted` when the code or type is `insufficient_quota` (or `billing_hard_limit_reached`), `retry_after` from the `Retry-After` header (seconds); code `moderation_blocked` (or the older `content_policy_violation`) → `ContentPolicy`; 408 → `Timeout`; other 4xx → `InvalidRequest` (e.g. an unknown model, 404); 5xx → `Server`. Transport: ureq timeouts and timed-out I/O → `Timeout`; host not found, connection failed, TLS and other I/O → `Network`; an answer over the limit → `BadResponse`. An answer without pictures, without `b64_json`, with bad base64 or no PNG → `BadResponse` naming the picture.
    - **Timeouts:** connect 20 s, whole request 180 s (OpenAI: complex prompts "may take up to 2 minutes"), both settings (`connect_timeout_secs` 1–120, `timeout_secs` 5–900).
    - **Cancelling:** the provider checks the token before sending, after the answer, after reading it and after decoding. A blocking request already sent cannot be stopped: its answer is read to the end (or the timeout) and thrown away. **A cancelled request may still be billed by OpenAI (UNVERIFIED);** the cost note says so.
    - **Cost note** (shown before generating): the description goes over the internet to OpenAI, every picture is billed to the user's own API account, no free tier, the price depends on model, quality and size (OpenAI's pricing page), a cancelled request may still be billed. No price is quoted: the per-picture cost of the 2.6 models is not published (only token prices).
    - **HTTP client:** `ureq` 3.5.2, blocking (no async runtime), on the job's worker thread; `default-features = false`, feature `native-tls-no-default`; TLS provider `NativeTls` with the platform's root certificates (`RootCerts::PlatformVerifier`): Security.framework on macOS, SChannel on Windows, OpenSSL on Linux and the BSDs. **Not rustls:** every rustls build pulls `ring` (Apache-2.0 AND ISC), `rustls-webpki` and `untrusted` (ISC), and ISC is not on the CLAUDE.md allowlist; the native-TLS build pulls no such crate (checked below). Linux therefore needs the OpenSSL headers at build time (`libssl-dev`, added to the CI apt line) and libssl at run time. HTTP(S) proxies from the environment are used (ureq's default). No gzip.
  - **API keys** (`secret`):
    - `SecretStore` trait (`kind`, `get`, `set`, `delete`) with `KeychainStore` (the `keyring` 4.2 crate, default `v1` stores: macOS Keychain, Windows Credential Manager, the Secret Service over D-Bus on Linux/BSD; service `DeluxePainter`, account `openai`) and `MemoryStore` (this session only).
    - `ApiKeys::system()`: the keychain when `keyring::Entry::store_status()` is fine, else no persistent store and the reason (e.g. Linux without a Secret Service daemon); keys are then kept in memory for this session only, and `ApiKeys::status(..).session_only` and `KeyStatus::describe()` ("API key kept for this session only (no system keychain)") let the GUI say so. When the keychain exists but refuses to store (locked, access denied), the key also goes to the session store and the reason is kept. Nothing is ever written to a settings or project file.
    - Lookup order: a key kept for the session (typed, not storable), the keychain, then the environment variable (`OPENAI_API_KEY`), which is read-only: a key typed into DeluxePainter wins, and clearing the key in DeluxePainter (`ApiKeys::clear`: keychain and session) leaves the variable, which the status then names. Keychain reads are cached for the session (each read may ask the user on macOS).
    - `Secret` is a key trimmed of surrounding whitespace and made only of printable ASCII without spaces (it goes into an HTTP header); its `Debug` shows only its length, and `ApiKeys`' `Debug` shows no key.
    - Tests use `MemoryStore`, a fake keychain and an injected environment reader only; no test touches the real keychain or the real environment.
  - **Jobs** (`JobManager`, `Clone + Send + Sync`, shared by GUI and MCP): `submit(provider, request) -> JobId` (`gen-N`, from 1) refuses at once, with nothing sent, a provider that is not set up, a request outside its capabilities and a third job while **2** run (`BUSY`: every generation may cost money; MCP clients must not start them without limit). Each job runs on its own `std::thread` (named `dpx-imagegen-gen-N`); states `running`, `done` (pictures kept as `Arc<Vec<RgbaImage>>`), `failed` (the `GenError`), `cancelled`. `status`, `list`, `images`, `cancel` (marks the job cancelled at once and sets its token; the late answer is thrown away), `forget` (finished jobs only), `wait(id, timeout)` (tests and MCP, never the GUI thread), `revision()` (increases with every change, cheap to poll each frame) and `set_waker` (called after every change, for egui's `request_repaint`). The **8** newest finished jobs are kept with their pictures; older ones go. A provider that panics fails its job (`BAD_RESPONSE`, "the image generator stopped unexpectedly"); an answer with no picture is a failure too.
  - **No fake generation:** `fixture::TestPattern` (id `test-pattern`, "Test pattern (not AI, debug only)", no network, no cost) draws a fixed landscape-like pattern varied by the prompt's hash, the seed and the variant, opaque or with a transparent sky. It exists for tests and a clearly marked debug snapshot flag (part 2) and is never in `user_providers`; a test checks that. Like a provider or a file decoder it only makes a true-colour source picture; no document pixel logic lives outside `dpx-core`.
  - **Conversion** (`dpx_core::import::convert(img, &ConvertOptions, &ConvertTarget) -> Result<Imported, CommandError>`), the one entry point for generated pictures (GUI and MCP):
    - `ConvertTarget`: the `Target` (chipset, mode, screen), the page size of the result (exactly), the current palette, the BG index and the transparent colour of a new palette (ADR-9's pink).
    - `ConvertOptions`: framing, scaler, margins, palette New/Current, colours, dither, transparent background. Defaults: Crop, Smooth, BG margins, New, 32, Floyd–Steinberg, opaque.
    - Checks first, converting nothing: a mode the chipset cannot show (`UNSUPPORTED_MODE`), a colour count that is no power of two in 2..=the mode's maximum (OCS LoRes 32, OCS HiRes 16, AGA 256) or a current palette larger than that (`PALETTE_RANGE_INVALID`), a page outside the target's page limits or an empty picture (`INVALID_ARGUMENT`).
    - **Transparency:** with `transparent_background` pixels with alpha below 128 become colour 0 (ADR-9: reserved, pink with a new palette, colour 0 of the current palette, which opaque pixels then avoid); without it the picture is laid on the BG colour first (alpha mixing) and comes out opaque.
    - **Framing** (no distortion either way; proportions are display proportions, page × pixel shape, `resample::display_aspect`): **Crop** fills the page: the centred part of the picture with the page's proportions (`resample::crop_to_aspect`; the extra pixel of an odd leftover goes right and below), scaled to exactly the page. **Fit** shows the whole picture as large as fits (`fitted_size`, ADR-42) centred, with **BG** margins (exactly ADR-42's margins: the BG colour counts for a new palette like that many pixels, takes no part in dithering, is the BG index with the current palette) or **Transparent** margins (colour 0, reserved like transparent pixels).
    - **Scalers:** **Smooth** = area averaging (`resample::scale_area`, ADR-9), **Nearest** = the source pixel under each page pixel's centre (`resample::scale_nearest`), **PixelArt** = a majority filter per page pixel (`resample::scale_majority`): the cell is the source pixels from `floor(o·src/dst)` to `ceil((o+1)·src/dst)` on each axis; colours are counted in buckets of 8 levels per channel (5 bits), so the slight noise of generated "pixel art" does not split one colour into many; the bucket with the most pixels wins (ties: the one met first in reading order) and gives the mean of its pixels; mostly transparent cells become transparent. Enlarging takes the pixel under each cell's top-left corner.
    - **Reduction:** ADR-42's (`reduce_fitted`): a new palette of exactly `colors` entries (median cut + k-means, exact when the picture has no more colours, rounded to 12-bit values on OCS) or the current palette; None / Floyd–Steinberg / Ordered. With the current palette on OCS its entries are rounded to 12-bit values first (a 12-bit palette stays identical), so the result always fits the chipset.
    - `Imported::replace_command(target)` makes the command below from the result.
  - **`Command::ReplacePicture { target, palette, width, height, pixels }`** (JSON op `replace_picture`), for a generated picture's "Picture" target: replaces the document's target (chipset, mode, screen), palette and frames by one page, keeps the frame rate (a setting), and is **one undo step** (`Footprint::Document`: the snapshot shares the old frames through `Arc`; the command's pixels and palette count for the undo byte budget). It checks its own target, not the document's: the mode must exist on the chipset, the palette must have a power of two of 2 up to the mode's maximum entries and be 12-bit on OCS (unlike `SetPalette`, which checks only the count), the screen must fit the mode and the page the target's page limits, and the pixels must be `width × height` colours inside the palette. **With the layers branch (ADR-44) merged it also resets the document to one layer** (a `TODO(wave8-integration)` in `Command::apply`).

- Decided without the owner:
  - Default model `gpt-image-2.6-flare` (current, the fast one, named as replacement on the deprecations page) and quality `medium`; both settings. `xhigh`/`max` quality, `moderation`, `output_compression`, streaming and partial images are not used.
  - The size choice (long side 1024, exact proportions up to a quarter larger) and Crop as the default framing: the request already has the page's proportions, so Crop cuts nothing or almost nothing, while Fit would leave one-pixel margins on rounding.
  - The majority filter's 5-bit buckets and its tie rule; enlarging by the top-left pixel.
  - Transparent pixels laid on the BG colour when transparency was not asked for; `background: opaque` sent explicitly.
  - 403 counted as an authentication failure (OpenAI uses it e.g. for organisations that must be verified first); 408 as a timeout.
  - At most 2 running jobs and 8 finished jobs kept; jobs are not persisted across restarts.
  - Key lookup order session → keychain → environment; keychain service `DeluxePainter`, account `openai`; the session fallback when the keychain refuses to store.
  - `ReplacePicture` needs a whole-bitplane palette and 12-bit entries on OCS (convert always gives that).
  - `User-Agent: DeluxePainter` without a version or contact; environment proxies respected.

- Consequences:
  - Linux builds need `libssl-dev` (and users libssl); macOS and Windows use the system TLS. A Linux distribution without libssl 3 compatible with the build is not covered.
  - A generated picture can be bought twice when the user cancels and generates again (the first may be billed).
  - Without a key (or with the variable unset) the provider is "not set up": nothing is generated, nothing is faked.
  - Model ids change often; an outdated default gives `INVALID_REQUEST` ("model does not exist") until the setting is changed.

Whether `gpt-image-2.6-flare` honours `background: transparent` (the guide says "either model"), its latency, its price per picture, whether a cancelled request is billed, and the exact wording of real error answers are UNVERIFIED.

  - The real keychain on any system (no test touches it), macOS prompts for unsigned builds, Linux with and without a Secret Service daemon, Windows Credential Manager.
