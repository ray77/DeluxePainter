# ADR-38: Anim control: Set Range, the Control Panel, Method and Move

- Status: accepted (Wave 7, 2026-11-11; decided without the owner, as CLAUDE.md allows for internal details; the visible choices without a clear answer in the manual are listed below as owner questions)
- Context:
  - ADR-28 left out Set Range, the Animation Control Panel (Alt-a), Method, Move and the keys Shift-1 … Shift-5. Manual (AGA PDF pages): Anim ▸ Control and the panel figure p.257 (Figure 8.32), Set Range p.257, Method p.258-259, Move p.252-255, keyboard table p.296; tutorial p.129-130 (frame counter, panel), p.137-140 (cyclic moves), p.148-149, p.151-163 (Move), p.182 (Set Range with key `4`), p.184-186.
  - The manual contradicts itself on Set Range: the reference (p.257) says Play once and Ping-pong use the range and Play does not; the tutorial (p.182) sets a range and plays it with `4` (Play), through Range / All Frames buttons.
  - The manual gives no formulas for Move: not the observer distance or perspective centre, not the ease curve, not the exact Cyclic / Come To mapping. It describes the visible results only.
  - Every picture change must be one undoable command on the one engine (ADR-2/6); pixel logic only in `dpx-core` / `dpx-raster`.
- Decision:
  - **Set Range** (Anim ▸ Control ▸ Set Range..): a "Set Play Range" requester with the radio pair All frames / Frames From … To and Ok / Cancel (the radio pair follows the Copy Frames deviation of ADR-28; DeluxePaint uses Range and All Frames buttons). From must be smaller than To; otherwise the requester stays open with "From n must be before To m". The range is used by Play once, Ping-pong and Play once backward, **not** by Play or Loop backward (reference p.257). A range beyond the last frame is cut there; if fewer than two frames are left, all frames play. The range lives in the app, not in the document or `.dpxproj` (no format change).
  - **Playback** (`dpx_core::anim`): `PlayMode` gains `LoopBackward` and `OnceBackward`; `frame_in(mode, first, last, position)` and `start_position` play a sub-range. Play, Loop backward and Ping-pong start at the current frame when it lies inside their frames (else at their start); the play-once modes start at the first (backward: the last) frame of theirs. `frame_at` is `frame_in` over all frames, so ADR-28 behaviour is unchanged.
  - **Keys** (p.296; paint screen, not while typing or under a modal): Shift-1 / Shift-2 first / last frame (held: repeats), Shift-3 the last Go To frame again (the Go to Frame requester before any Go To), Shift-4 loop backward, Shift-5 play once backward, `M` (Shift-m; plain `m` stays Magnify) the Move requester (it runs the menu item, so it ends Stencil ▸ Paint as the item does, ADR-39), Alt-a the panel. Shifted digits are read from the physical key (`Event::Key::physical_key`), because they type `!`, `"`, `§`, `$`, `%` … depending on the layout. egui-winit 0.37 reports `logical.or(physical)` as the key (checked in its source), so macOS Option-a (which types `å`) arrives as `A` with Alt.
  - **Control Panel** (Control ▸ Panel On/Off, Alt-a): a 21-pixel bar at the bottom of the UI screen, left of the toolbox (full width when the toolbox is hidden), drawn over the page like the toolbox. Top row: First Frame button, slider, Last Frame button; bottom row: the ten control buttons in the order of Figure 8.32 (loop backward, play once backward, previous, next, play once forward, loop forward, ping-pong, add, delete, Go To), then LightTable, `2`, `P`, `N`, `S` at the right end. Icons are drawn for this project (no original artwork). The toggles show the Light Table state (ADR-28). Buttons act on press and show pressed until the button goes up. A click left / right of the knob steps one frame (p.257; no wrap); the knob drags to the nearest frame. Add and Delete run the ADR-28 frame commands (one undo step each) through the same path as the menu's frame items (`frame_command`), so an area stencil and Stencil ▸ Paint follow their picture (ADR-39). Go To repeats the last Go To; Ctrl-/Cmd-click or the right button opens the Go to Frame requester (p.257: Ctrl-click). The panel's visibility is not saved.
  - **Method** (Compressed / Expanded): a radio pair with a check mark (Compressed by default). It only describes DeluxePaint's RAM model (p.258-259), so it changes nothing here, adds no command and is not saved.
  - **Move** (`M`, Anim ▸ Move..): the Move requester (248×142 UI pixels, square corners): Dist X/Y/Z and Angle X/Y/Z with a Brush toggle each, Clear, Go Back, Cyclic, Ease-Out, Ease-In, Count, Direction Move (Go From / Come To) and Record (Forward / In Place / Backward), Preview, Trails, Fill, Draw, Cancel, Load, Save, Exit. Return = Draw, Esc = Cancel, Tab / Up / Down as in the other requesters, `-` only at the start of a signed number.
    - `Command::MoveBrush` (JSON op `move_brush`) paints the whole move as **one undo step** over every frame it touches (`Footprint::Frames`), with the paint fields of `Stroke` (brush or custom brush, colour, mode, range, stencil, effects). `dpx_core::anim_move` holds the pure parts: `plan` (eased path, frames), `project` (perspective, nearest neighbour), `outline` (wire frame), `validate` / `apply`. The GUI, CLI (`--commands`) and MCP use the same command. A refused move (e.g. more than `MAX_PAINT_WORK`) keeps the requester open with the reason and does not touch the remembered settings, so Cancel afterwards still restores the ones from before (p.255); only a move that was drawn (and Exit) keeps new settings.
    - Two optional fields (added after the wave-7 review; JSON without them reads as before): `area` (`FrameArea`: an area stencil and its frame; only stamps on that frame are tested against it, ADR-39) and `view` (`MoveView`: the start pose `at` with its orientation `rot`, and the observer's `center` and `distance`). Without `view` a move starts unturned at the `start` pixel and uses `EYE` and the page centre. Validation refuses a view whose numbers are not finite, whose `at` lies outside the `start` pixel, whose centre or distance is out of range, or whose `rot` is not a rotation, and an area of the wrong size or for a frame the document lacks. Projection uses Perspective's ray casting (`perspective::Placement::local`, ADR-37), so a move stamp equals the perspective stamp of the same pose and observer.
    - The GUI always sends `view`: the observer is Effect ▸ Perspective's centre and distance (the middle of the screen and the screen width until they are set; on a 320-pixel-wide screen that is the old `EYE`), and the start is whichever came last: the end of the last move (with its orientation), a click on the page (unturned) or a perspective stamp (its exact pose); the page centre before any of them. It sends `area` while an area stencil is on.
    - Stencil ▸ Show keeps painting off for Move too (ADR-31): Draw and Trails leave the requester open with "Stencil Show is on: nothing is painted". While Preview plays, the Move frames and wire frame show as they are, without the Stencil view.
    - Work of a move (validated against `MAX_PAINT_WORK`): one unit per brush pixel, then per painted stamp (Trails repeat earlier stamps, about Count² / 2 of them) one unit, plus per page pixel the projected stamp covers one to project and `pixel_work` to paint, plus, in the modes that read the page as it was before the stamp (Shade, Cycle, Blend, Mix, Smooth, HBrite, and Matte / Color / Replace with an effect on), the pixels of the stamp's rectangle and one pixel around it. Nothing a stamp does costs the whole page or the whole brush: those modes keep one page-sized copy of the page and refresh it before each stamp only in that rectangle (the only pixels `plot_fx` reads; Smooth reads the eight around a pixel), Smear reads the page itself and needs no copy, and the colour around a projected brush without a transparent colour is found once per move (finding it reads the whole brush).
    - Coordinates: page X right, Y down, Z away from the viewer; the requester's Y distance counts up (DeluxePaint) and is negated. Positive Z angle = clockwise on screen, positive X angle tilts the top away, positive Y angle turns the right side away. Screen axes rotate in Euler order X, Y, Z (p.253); brush axes rotate incrementally about the brush's own turning axes; Dist ▸ Brush moves along the turning brush axes.
    - Count stamps are painted. Cyclic (default on) splits the path into Count steps and leaves out the end (it is where a loop starts again, tutorial p.137-139); without Cyclic Count − 1 steps and the last stamp shows the end. Go From starts at the stamp on the current frame; Come To ends there and starts Count − 1 frames earlier. Frames wrap; with one frame or Record ▸ In Place every stamp goes to the current frame; Backward paints the same frames from the last one back (matters with Trails). Afterwards the frame of the last stamp is current; Forward Go From with Cyclic moves on to the frame after it (tutorial p.140).
    - Trails paints every earlier stamp of the move on each frame as well. Preview plays the wire frame (in FG) one stamp per frame time at the animation rate; Space, Esc or a click stop it, and the requester comes back. Exit keeps the settings without drawing; Cancel keeps the old ones.
- Decided without the owner (DeluxePaint gives no answer; the most DeluxePaint-like option):
  - Observer distance `EYE` = 320 page pixels (a brush 320 pixels away shows at half size), projection centre = page centre, for `move_brush` commands without a `view` (CLI, MCP); the GUI uses Effect ▸ Perspective's observer instead (wave-7 review, after AGA p.193, where moves shrink towards the perspective centre). Corners closer than 1 pixel to the eye are not drawn (that stamp is skipped).
  - Ease-Out = speeds up over that many steps at the start, Ease-In = slows down at the end, with constant acceleration (trapezoid speed profile); ease steps that do not fit are shortened in proportion. The research notes warn that the manual's OCR may swap the two words.
  - Count starts at the number of frames (tutorial p.152); later the last Exit / Draw settings come back (Trails is not remembered). The next move starts where the last one ended, with its position, depth and orientation, unless Go Back; a brush click on the page sets the start again (unturned), and a perspective stamp sets it to that stamp's exact pose, so the Moving Ground recipe (turn, stamp, Undo, Move, AGA p.192) starts from the turned brush. (Before the wave-7 review only position and depth carried over.)
  - Wave-7 review: Draw and Trails are refused with a message while Stencil ▸ Show is on; `M` ends Stencil ▸ Paint like the menu item; a move spares an area stencil on the stencil's own frame only; Preview shows its frames without the Stencil view. Visible.
  - Clear zeroes the six Dist and Angle numbers only.
  - Fill (a filled perspective plane), Load and Save (move files; their format is not described) are always ghosted; Trails and Record are ghosted with one frame (p.254).
  - Built-in brushes are projected as a custom brush in FG; Replace mode fills the projected bounding box like the other brush transforms (`rotate_any`).
  - Delete on the panel asks no confirmation (DeluxePaint asks, tutorial p.130), because here it is undoable.
  - The panel's exact pixel size, its place left of the toolbox and the icon designs.
  - Shift-3 with no Go To yet opens the Go to Frame requester.
- Not done: `r` (reverse during playback) and the arrow keys (speed) from p.296, Move ▸ Fill / Load / Save, animpainting, AnimBrush. The ADR-28 "Not yet" list is otherwise covered here. The stale ADR-28 comment in `menu.rs` ("Move, Panel, Set Range and Method stay ghosted") was left as it is to avoid conflicts with parallel branches.
- Owner questions:
  - Should Set Range also limit Play (`4`), as in the tutorial (p.182), instead of only Play once and Ping-pong (reference p.257)?
  - Is the perspective strong enough? The GUI now uses Effect ▸ Perspective's observer (screen width in front of the screen centre until set); `move_brush` without a `view` keeps 320 pixels in front of the page centre.
  - Should Delete on the panel ask for confirmation as in DeluxePaint, although it is undoable here?
  - Panel place and size: bottom of the screen, left of the toolbox, over the page.
- Verified:
  - Unit tests (`dpx-core`): easing always arrives and speeds up / slows down; Go From with Cyclic leaves out the end and moves past it; Come To ends on the stamp and the current frame; Record In Place / Backward; rotation direction and that a cyclic full turn never shows twice; brush-axis distances follow the turning brush; the unmoved projection is the brush itself; depth shrinks towards the centre; built-in brushes and outlines; Draw paints one stamp per frame in one undo step; Trails / Backward with the stencil; bad moves are refused; ranges and backward playback in `anim`.
  - Unit tests (`dpx-ui`): panel layout, every button is hit where it is drawn, knob position and drag, toggles and held buttons; Set Range All / From-before-To; the Move requester reads back its settings, signed typing, toggles and icons, bad numbers keep it open, ghosted buttons do nothing, both requesters fit the smallest screen.
  - App tests through `PainterApp::ui` with real egui key and pointer events (as the idle window runs, with egui's own repaint delays): Shift-2 (German `"`), Shift-1 (US `!`), Shift-3 before and after a Go To, Shift-4 / Shift-5 (the latter shows frames 5 → 1 and stops on 1); Shift-M opens Move, Return draws over four frames from the clicked point, `U` undoes the whole move; Alt-a (as macOS Option-a) shows and hides the panel; Panel On/Off, Set Range.., Method ▸ Expanded / Compressed and the top-level Move.. picked with the right button in the menu strip; Set Range Frames 3-6 then `4` from frame 10 starts there while `5` plays 3-6 and stops on 6; Preview through the pointer plays all ten frames and brings the requester back without drawing; every panel button clicked with the pointer (First, Last, Previous, Next, Add, Delete, LightTable, the five play buttons, Go To with the right button), slider steps both ways and the knob dragged to the last and back to the first frame, with nothing painted under the panel. Further app tests call the handlers directly (refused move keeps the reason, Go Back, preview frames).
  - Three mutations (Shift-4 playing forward, the range ignored, the knob drag arm removed) each made the new ui() tests fail.
  - Review fixes (each test failed with the old code put back, and passes now): `trails_in_a_reading_mode_do_not_copy_the_page_per_layer` (Shade, Count 200, Trails, 2 frames on a 4096×4096 page: 19 s in a debug build with a whole-page copy per stamp, 0.07 s now; the test allows 2 s); `trails_with_an_opaque_brush_do_not_scan_the_brush_per_layer` (a 2048×2048 brush without a transparent colour, a few pixels wide at depth 200 000, Count 40, Trails: 15 s with the colour search per stamp, 0.08 s now); the app test `cancel_after_a_refused_move_brings_back_the_settings_from_before` (through `PainterApp::ui`: Shift-M, Return draws, Shift-M, typed Dist Z -310 and Count 999, Trails clicked with the pointer and refused, Esc, Shift-M shows the drawn settings again; it showed the refused ones before). `reading_modes_see_the_page_as_before_each_stamp` checks that Smooth, Shade, Blend, Cycle and translucent Matte with Trails paint exactly what stamping every layer as a command of its own paints; it fails when the refreshed rectangle loses its one-pixel margin. The review's CLI cases (`--snapshot --page 1008x1024 --frames 2 --commands`, debug build), measured again with the fix: a 1-pixel brush, Count 999, Trails takes about 1.3 s in Smear, Matte and Shade alike (the review measured 11.2 s for Smear and 1.1 s for Matte; what is left is the fixed cost of the 499 500 stamps), and the 1000×1000 opaque brush at depth 100 000, Count 60, Trails 0.24 s (the review: 5.7 s), as fast as with `transparent: 0`. Not measured in a release build. A `--commands` snapshot of a turning Shade move with Trails over 8 frames was looked at: frame 8 shows the eight stamps one Shade step up and two steps where they overlap.
  - Wave-7 review fixes, each test failing with its fix taken out again: unit tests (`dpx-core`) `an_area_stencil_spares_its_own_frame_only` and `a_view_starts_turned_and_projects_as_perspective_does` (a quarter turn about Z at depth 50 and Euler 20/−30/10 at depth 30 equal `perspective::project_brush` pixel for pixel; bad views refused); app tests (the panel and the requester through their handlers, Ctrl-s and Shift-M as egui key events through `ui()`) `the_control_panels_add_and_delete_move_the_stencils_with_their_picture`, `shift_m_ends_stencil_paint_and_the_move_spares_the_area_stencil` (fails without the menu path for `M` and without the `area` field), `move_paints_nothing_while_stencil_show_is_on`, `the_move_preview_keeps_its_wire_frame_under_stencil_show`, and `a_move_after_a_perspective_stamp_starts_from_the_turned_brush` (ADR-37). The older Move unit tests pass unchanged with the shared ray casting.
  - Snapshots (`--anim-panel`, `--anim-control range|move`, and `--commands` with a `move_brush` op over 8 frames with the Light Table) were rendered and looked at.
  - Not verified: a real keyboard and mouse in the window (Shift-digits and Option-a on real layouts, Windows / Linux), DeluxePaint's exact perspective and ease formulas, and the panel's exact look against a real Amiga.
