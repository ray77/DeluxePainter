# ADR-46: Chipset choice, screen presets and hardware rules on export

- Status: accepted (2026-11-12, wave 8 strand "modes and presets"; built from the owner's implementation spec "DeluxePainter – MCP-Anbindung und KI-Bildgenerierung" §3 and §8 and the owner's wave-8 decisions; the points under "Decided without the owner" were not asked)
- Context:
  - The spec asks for a chipset choice (OCS/AGA) and presets when a picture is made, with 320×240 offered prominently but never labelled as standard PAL or NTSC, OCS 12-bit colours, and IFF/ILBM exports that respect the real chipset and mode limits ("never exceed them silently"; "explain 320×240 as a custom format on every export option; do not promise exact hardware compatibility").
  - Before this ADR the GUI could not choose the chipset (`Command::SetFormat` had no chipset field; OCS documents came only from `.dpxproj` or MCP `new_document`). The hardware check (`validate_hardware`) existed only in `dpx-mcp`; the GUI's Export, Anim ▸ Save and the CLI `convert` wrote without it. On OCS, `SetPalette` accepted any 24-bit colour, `SetFormat`'s grey ramp was not 12-bit (#242424 and the like), and reading a `.dpxproj` checked only the screen size (scouting notes, verified live over MCP).
  - Owner decisions for wave 8 (binding): no ECS (chipsets stay OCS and AGA); all UI strings English; the Import requester of ADR-42 stays as it is.
- Decision:
  - **`Command::SetFormat` gains `chipset: Option<Chipset>`** (`serde` default `None` = keep the current chipset; not serialised when `None`, so older JSON and command files are unchanged). The mode, the colour count and the screen are validated against the resulting chipset ("PAL:Super-High Res is not available on Ocs", "32 colours: PAL:High Res allows 2..=16 (powers of two)"). Undo restores the whole previous document, target included (a document snapshot, as before). All existing callers pass `None`; the Screen Format requester always sends its chipset. When Retain Picture keeps a colour the new chipset and mode cannot hold, the refusal says so instead of asking for an impossible count: "the picture uses colour 31; PAL:High Res on Ocs has at most 16 colours (turn Retain Picture off)".
  - **OCS colours are 12-bit, a document rule:**
    - `SetPalette` on an OCS document refuses an entry that is not 12-bit (`PALETTE_RANGE_INVALID`, e.g. "colour 2 #010203 is not a 12-bit OCS colour (each channel a multiple of 0x11, e.g. #000000)"). AGA takes any colour.
    - `SetFormat` on OCS snaps every entry of the new palette to the nearest 12-bit value: the grey ramp for new entries, and the kept entries of an AGA palette when the chipset changes to OCS (rounded, not refused: the change is an explicit, undoable user action). The rounding is never silent: the engine counts the kept entries it rounds in the new **`Outcome::rounded_colors`** (`Command::rounded_colors`, also for a dry run and a redo; new grey-ramp entries do not count), the GUI names them in a note "Screen format changed: N colours rounded to 12-bit OCS values", and MCP's `execute_command`/`undo`/`redo` result carries `rounded_colors` (left out when 0), since a rounded entry can even become the same colour as another (#080808 → #000000). The `execute_command` argument description now lists `chipset` (ocs|aga) among the `set_format` fields and says that it rounds.
    - Reading a `.dpxproj` checks the target's colour limits, not only the screen: the chipset shows the mode, the palette fits the mode's colour count, OCS entries are 12-bit (`hardware::check_palette`). A project that breaks them is refused with the new `ProjectError::Hardware` ("Project breaks hardware rules", details e.g. "palette entry 17 is not a 12-bit OCS colour.").
    - **Audit of every GUI path that writes palette entries on an OCS document:** Color Mixer RGB and HSV sliders (OCS levels 0–15 stored ×17, ADR-16) and Spread (in 4-bit levels) give 12-bit colours, Copy/Exchange move entries of a 12-bit palette (new test over a mixed sequence of edits); colour ranges and cycling change only the shown palette; Default Palette is the 12-bit start-up palette; **Restore Palette** now rounds (a note "Palette restored" names them; the palette of the last loaded picture is 24-bit when an AGA picture was changed to OCS); **Palette ▸ Load..** now rounds the file's colours with a note in "Palette loaded"; **Use Brush Palette** (custom brush and AnimBrush) rounded only a recomputed palette (ADR-39) and now also a palette taken as it is (`brush_palette::use_cels_palette`), with a note; Recompute is ghosted (HAM only) and writes nothing; Metamorph maps cels to the nearest picture colours and writes no palette; Import with a New palette rounds in the quantizer (ADR-42 tests) and with the Current palette keeps the document's 12-bit palette; Arrange is a permutation; Picture ▸ Load / `--open` of ILBM, PNG and JPEG open as AGA (files store no chipset); the spare page takes the shown page's palette and target; Screen Format snaps as above.
  - **`dpx_core::hardware`** (new module): the rules of MCP's `validate_hardware` moved to core, in the same order, with the same messages and the `HARDWARE_LIMIT` code: (1) the chipset shows the mode, (2) the palette has at most the mode's colours, (3) the page is within `Target::page_limits`, (4) OCS entries are 12-bit, (5) every pixel is a palette colour (now over every animation frame, not only the current one). `dpx_mcp::pictures::validate_hardware` is a thin wrapper, so the parallel live-MCP branch merges cleanly. `validate_picture` is the same check with one difference: a page smaller than the screen passes (brush-sized picture files, and `convert` keeps a picture's own size); the GUI's and the CLI's IFF exports use it. Helpers: `depth`, `is_12_bit`, `snap`, `snap_colors`, `first_unshowable`, `check_palette`, `rounded_note`.
  - **`hardware::format_notes(&Target)`**: honest notes for exports, empty for a standard screen. A custom size: "320x240 is a custom screen size on PAL:Low Res (standard 320x256); exact hardware compatibility is not guaranteed", plus, when the screen is wider or taller than standard, "320x240 uses vertical overscan (at most 368x241 on NTSC:Low Res)" (horizontal / horizontal and vertical likewise); the full overscan size: "368x283 is the full overscan screen of PAL:Low Res (standard 320x256); exact hardware compatibility is not guaranteed". **`hardware::iff_notes(&Target, page)`**: "IFF files store no chipset: this OCS picture reopens as AGA" for OCS, and "the file reopens as PAL:Low Res (an OCS display mode carries no PAL/NTSC monitor)" when `DisplayMode::guess` on the written CAMG and the page size gives another mode (e.g. an OCS NTSC picture taller than 200 lines). **`hardware::export_notes(&Document, iff)`** gives both for an export format; the GUI's and the CLI's exports and MCP's `save_picture` use it, so all of them name a custom screen and, for IFF, the lost chipset.
  - **Exports (`apps/deluxepainter/src/files.rs`):** `check_hardware(doc, format)` runs `validate_picture` for IFF ILBM and IFF ANIM; PNG stays a free exchange export and the `.dpxproj` project is lossless, so neither is checked. `encode_document` (GUI Export, Anim ▸ Save, autosave, CLI `convert` through a document) refuses with "not written as IFF: <rule>"; the direct ILBM/PNG → ILBM path of `convert` (`save`) checks and names the file it writes: the target that file reopens with (`picture_target`, factored out of `open_picture`), read from the ILBM about to be written. An ILBM is copied as it is; an indexed PNG becomes an ILBM whose page fields hold the picture's own size and no CAMG (as before), so a 320×240 PNG is written as a 320×240 custom-screen ILBM and named as one (it was first checked and named with the 320×256 screen the PNG would open on, which the file does not hold). The direct ILBM → PNG path names the ILBM's screen, which the PNG loses; PNG → PNG gives no screen note (neither file holds a screen). Every IFF and PNG export through the document adds `format_notes`; IFF exports add `iff_notes`. MCP's `save_picture` (`dpx_mcp::pictures::encode_document`) gives the same notes. The CLI prints the notes to stderr as `note: …` and a refusal as the error (exit code 1, nothing written).
  - **GUI refusal:** Picture ▸ Export.. and Anim ▸ Save.. check before asking about overwriting; a refused file closes the file requester and shows the note requester "Picture not exported" / "Animation not saved" with the broken rule and "An IFF picture must fit its display mode: change it with Picture > Screen Format, or export PNG". Nothing is written. A successful export shows the format and IFF notes in the existing "Picture exported" / "Animation saved" note.
  - **Presets (`dpx_core::mode::Preset`, `PRESETS`):** id, label, display mode and screen size, in this order: `ntsc_lores` "NTSC LoRes 320x200", `pal_lores` "PAL LoRes 320x256", `pixel_art_320x240` "Pixel art 320x240 (custom)" = PAL:Low Res with a custom 320×240 screen, `ntsc_hires` "NTSC HiRes 640x200", `pal_hires` "PAL HiRes 640x256", `ntsc_hires_laced` "NTSC HiRes Laced 640x400", `pal_hires_laced` "PAL HiRes Laced 640x512", `custom` "Custom" (no format). 320×240 is PAL:Low Res with a screen 16 lines shorter than standard because that variant keeps its mode when an OCS ILBM is read back: OCS CAMG carries no monitor bits, so PAL/NTSC comes from the height, and 240 lines read as PAL (NTSC 320×240 needs vertical overscan and reads back as PAL; scouting notes, verified live). `Preset::by_id`, `index_of(mode, screen)` (else Custom), `target(chipset)`, `is_standard`. The labels name no standard for 320×240.
  - **Screen Format requester (documented deviation from DeluxePaint IV, which has neither gadget):** a new row below Palette Size: **Preset** (cycle gadget, left column, as wide as the Screen Size row) and **Chipset** (cycle gadget OCS/AGA, right column under Credits). The window is 30 pixels taller (206 → 236 of the 256-line requester screen); Use and Cancel moved down from y 198 to 228; every other gadget keeps its place. Keys: `p` cycles Preset, `h` cycles cHipset (underlined in their labels); Up/Down, Tab, digits, Enter, Esc, `u`, `c`, `r` work as before.
    - Preset shows the preset that the selected mode and screen size match, else Custom, and follows every change made with the other gadgets (mode list, Screen Size, typed custom size). Cycling picks the next preset the chipset can show: it selects the mode, sets the screen (Standard for a standard size, else Custom with the size in the number fields), makes the page the screen ("Screen") and limits the palette size to the mode's maximum. Cycling to Custom keeps mode and screen and opens the screen size for typing (Screen Size becomes Custom).
    - Chipset switches OCS ↔ AGA: the mode list keeps only the modes the chipset shows (no SuperHiRes on OCS), the selected mode stays, the palette size is limited to the mode's maximum (AGA 256 → OCS LoRes 32 / HiRes 16), and the information panel's "Chipset" and "Max Colors = N of 4096/16777216" follow. While a SuperHiRes mode is selected OCS is impossible: the gadget is ghosted (grey text and glyph) and pressing it says "Super-High Res needs AGA".
    - Preset shows Custom once it is picked with the gadget, until the mode or the size really changes: keys that change nothing (a cursor key, Up on the first row, a click on the selected mode) leave it, so the next press goes on to the first preset instead of back to Custom.
    - Use sends the chipset. A refusal's message is now wrapped inside the information panel (up to four lines) instead of running past its edge: a bar inside the panel's bevel that ends on its last inner row, one row above and below each line of text (10, 21, 32 or 43 rows); the information lines it would cut into are left out whole (one message line keeps all six, two keep four, three keep three, four keep two), never shown in part. The message describes the command it refused: anything that changes the command Use sends (Retain Picture by click or `r`, Page Size, the mode, the size, the palette size, Preset, Chipset) clears it.
  - **Snapshot options:** `--chipset ocs|aga` and `--preset ID` set the picture up (one SetFormat that keeps the picture; the page becomes the preset's screen); `--requester-keys K,K..` feeds keys to `--requester` first (`up`, `down`, `tab`, `enter`, or one character), a refused Use shows its message, an accepted Use or Cancel is an error; `--export-note NAME` shows the note Picture ▸ Export.. would show for that name without writing anything. Bad values exit with code 2.
  - **Code:** rules, notes and presets in `dpx-core` (`hardware.rs`, `mode.rs`, `command.rs`, `brush_palette.rs`); the project check in `dpx-formats` (`project.rs`); the requester in `dpx-ui` (`requester.rs`, plus `NoteRequester::notes` for tests); the app glue in `apps/deluxepainter/src/screen_format.rs` (refusal note, rounding notes, snapshot options) with small hooks in `main.rs`, `files.rs`, `menu_actions.rs` and `palette_stencil.rs`.
  - **Dependencies:** none added (no new crate in `Cargo.lock`).
- Decided without the owner:
  - Rounding instead of refusing when Screen Format changes an AGA picture with 24-bit colours to OCS (refusing would leave no way in the GUI to make such a picture OCS); the note names how many colours were rounded. Palette ▸ Load, Restore Palette and Use Brush Palette round with a note for the same reason.
  - The layout of the new row, its labels, the `p`/`h` keys, "Super-High Res needs AGA", and the window growing downwards rather than changing the original gadgets or the Credits panel.
  - Picture and brush files may be smaller than their screen (`validate_picture`); MCP keeps the stricter page rule.
  - A refused export closes the file requester (the note explains; a new name would not help) and is checked before the overwrite question.
  - Format notes on PNG exports too (the spec asks for every export option); none on Picture ▸ Save (the lossless project) and none when the format is chosen.
  - The chipset spelling in messages stays `Ocs`/`Aga` (Rust debug form, as the existing MCP and engine messages), so MCP's texts do not change in this wave.
  - `ProjectError::Hardware` with its own summary rather than "Project file is damaged".
  - MCP's `set_format` to OCS rounds like the GUI and reports the count (`rounded_colors`), rather than being refused unless a `round: true` flag is sent: one engine rule for every front-end, and the result says what changed.
  - The direct PNG → ILBM conversion keeps writing the picture's own size into the page fields (no CAMG); its notes now follow that file, rather than the file being given the 320×256 screen the PNG would open on.
  - The message bar leaves out whole information lines (and is one row shorter than before, so a one-line message keeps all six) rather than moving elsewhere in the window.

## Integration (wave 8)

Strand B of the wave-8 integration closes two seams of this ADR and changes one of its consequences.

- **One preset table.** `dpx_core::mode::PRESETS` is the only list of screen presets: the Screen Format requester's Preset gadget, the Generate requester's Resolution (ADR-45) and MCP's `preset` argument all read it.
  - Generate requester (`crates/dpx-ui/src/generate_requester.rs`, `TODO(wave8-integration)` resolved): `RESOLUTIONS` is derived from `PRESETS` at compile time (a `const fn` over every preset but the closing Custom; a preset without a screen before it fails the build). `ResolutionPreset` gained the preset's `id`; its labels are the presets' labels, unchanged ("NTSC LoRes 320x200" and so on), and the default stays the 320×240 pixel-art preset.
  - MCP (`PresetArg` in `crates/dpx-mcp/src/tools.rs`, `TODO(wave8-integration)` in `mode.rs` resolved): the names ADR-43 gave (`ntsc_lores`, `pal_lores`, `pixelart_320x240`, `ntsc_hires`, `pal_hires`, `ntsc_interlace`, `pal_interlace`) stay; the presets' own ids (`pixel_art_320x240`, `ntsc_hires_laced`, `pal_hires_laced`) are accepted as aliases. `PresetArg::format` looks the preset up by id in `PRESETS`; there is no second copy of modes and sizes.
  - Tests that they agree: `dpx-ui` `resolutions_are_the_shared_presets` (ids, labels, display mode and screen of every entry against `PRESETS`, the label list unchanged, the default, the gadget's choices); `dpx-mcp` `presets_are_the_shared_table` (every `PresetArg` in `PRESETS` order, its name and alias parse, its format is the preset's).
- **Older OCS projects with colours that are not 12-bit open.** The first build of this ADR refused them (Consequences above: "no longer opens; nothing in this build can repair it"). That is replaced:
  - The project reader (`crates/dpx-formats/src/project.rs`) checks only the palette's size against the target (`hardware::check_palette_size`, rules 1 and 2); the colours are kept exactly as stored. Project format versions are unchanged (no new version, no new field; version-1/2/3 files read and write as before).
  - Opening such a project gives a note naming the entries and what follows, and a second one how to fix it. `hardware::stored_palette_note` (with `unshowable_entries` and `index_list`, which writes runs of three or more as `a-b`; the caller names what refuses the picture, see the review fixes below): "palette entries 9-27, 29, 30 are not 12-bit OCS colours (kept as stored); IFF export refuses the picture until they are 12-bit" (singular form for one entry). The GUI's fix line (`files::OLD_PALETTE_FIX`): "to fix them, use Picture > Screen Format.. with the OCS chipset (it rounds them to 12-bit colours and says how many), or choose AGA there".
