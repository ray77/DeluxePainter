# ADR-21: MCP spike and CI

- Status: accepted (Phase 1, 2026-11-10); implements the first slice of ADR-5.
- Context: ADR-5 fixes one binary, rmcp, stdio first, MCP off by default, logs on stderr only, files only in approved directories. Phase 1 needs a thin end-to-end proof that an MCP client can drive the same `Engine` the GUI uses, and a CI gate on all three platforms.
- Decision:
  - New crate `dpx-mcp` (depends on `dpx-core` only). `deluxepainter mcp` (exactly that, no other arguments) calls `dpx_mcp::run_stdio_blocking()`: a private tokio runtime, rmcp 3.9.0 (Apache-2.0; features `server`, `macros`, `transport-io`), stdio transport. It never starts the GUI. stdout carries protocol only; the one status line goes to stderr.
  - "Off by default" means: the GUI never opens an MCP channel, and nothing listens unless a client launches `deluxepainter mcp` itself.
  - Spike mode is the **headless in-process engine** from ADR-5. The bridge to a running GUI (interprocess socket) is Phase 7.
  - Tools: `app_status` (name, version, transport, engine kind, document summary), `new_document` (chipset, video, resolution, interlace, colours, width, height; validated by running the engine's `SetFormat` command on a scratch engine, so it follows the Screen Format rules and error codes; a rejected request leaves the current document untouched; success installs a fresh engine at revision 0), `get_document_state` (width, height, chipset, display mode, screen size, palette length, revision, `can_undo`, `can_redo`). Tool failures are `isError` results with the stable error code in the text.
  - No pixel logic in `dpx-mcp`; no file access yet, so the approved-directory rule has nothing to enforce. It will be implemented together with the first file tool (canonicalised paths, symlink-safe).
  - `get_document_state` reports `can_undo`/`can_redo` rather than an undo depth, because `Engine` has no depth accessor; a depth can be added when the engine exposes it.
  - CI (`.github/workflows/ci.yml`): fmt check, clippy `-D warnings`, `cargo test --workspace` on macos-latest, windows-latest and ubuntu-latest; toolchain from `rust-toolchain.toml` via `rustup toolchain install`; `Swatinem/rust-cache`; Ubuntu installs the X11/Wayland/GL/Vulkan development packages that eframe 0.37 (default features: wgpu, winit with x11 and wayland) may need.
- Verified (macOS, local): unit tests of the handlers; an integration test (`apps/deluxepainter/tests/mcp_stdio.rs`) that spawns the real `deluxepainter mcp` and runs initialize, tools/list, tools/call `app_status`, `new_document`, `get_document_state` and an invalid `new_document`, asserting every stdout line is a JSON-RPC message; a manual run with piped JSON-RPC.
- Not verified: the CI workflow itself (it cannot run locally); Windows and Linux builds and tests; the Ubuntu package list (a superset chosen from the dependency tree, not tested); behaviour with real clients (Claude Desktop/Code, MCP Inspector); the stateless `2026-07-28` protocol era (only a legacy `initialize` client was exercised).
- Consequences: rmcp, tokio and schemars enter the dependency tree of the app binary; rmcp handles requests concurrently, so a client that pipelines requests without waiting for responses may see them answered out of order (JSON-RPC ids keep them matchable).
