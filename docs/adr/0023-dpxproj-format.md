# ADR-23: The `.dpxproj` project format, version 1

- Status: accepted (Phase 4 start, 2026-11-10)
- Context: CLAUDE.md says Save = `.dpxproj` (lossless project) and Export = IFF ILBM / ANIM / PNG. ADR-1 and ARCHITECTURE §6 sketched a ZIP with tiled zstd cels and a separate `dpx-project` crate. The document is still one indexed page with a palette and a target, so the first version should be small, inspectable and checkable; layers and frames follow in later phases.
- Decision:
  - **Container:** ZIP (`zip` crate 9, MIT, `default-features = false`, only `deflate-flate2` with flate2's pure-Rust backend; no zstd, bzip2, aes, time). Entries `manifest.json`, `frames/0/layers/0.png`, optional `spare/page.png`. Layer images are 8-bit indexed PNGs with the palette in `PLTE`, written by the existing `png_io::write_png`, so they open in any image viewer and indices are exact. Details and the full manifest: `docs/PROJECT_FORMAT.md`.
  - **Where:** `crates/dpx-formats/src/project.rs` (not a new crate: it needs only core types and the PNG code that lives there). `Project { document, extras, spare }`; `ProjectExtras` / `ProjectRange` mirror the app's `PictureExtras` / ILBM `ColorRange`, so `dpx-formats` does not depend on `dpx-iff` or the app. `files.rs` maps between them (`From` impls).
  - **Manifest** holds format name and version, app version, target (chipset, mode, screen), page size, palette as `#RRGGBB`, ranges, grab point, transparent colour, and `frames[].layers[]` with exactly one frame and one layer for now. Unknown fields are refused; a newer `format_version` gives an error naming the version.
  - **Reader validates everything:** ZIP magic, names (no traversal, absolute paths, backslashes, directories, duplicates), exact entry set, entry-count / total-size / manifest-size / pixel limits (declared sizes checked before inflating, real bytes capped while reading), PNG header kind (8-bit indexed), size, palette and no tRNS.
  - **Writer is deterministic:** fixed entry order, time stamp 1980-01-01, permissions 0644, deflate, `serde_json` pretty output with a fixed field order.
  - **Round trip is exact** for pixels, palette, target (including the screen size), page size, ranges, grab point, transparent colour and spare page. Not saved: undo history and the revision counter (a loaded document is at revision 0).
  - **App:** `files::load` detects a project by the ZIP magic; `Picture::Project` carries it. `kind_of_path` and `save_format` accept `.dpxproj` (`SaveFormat::Project`), so `encode_document` writes projects too. `convert` sends projects and everything written to `.dpxproj` through the document (`open_picture` + `encode_document`), so ILBM to `.dpxproj` guesses mode and screen exactly like opening the ILBM in the GUI. `info` describes a project. A project never drops anything, so it emits no notes (ranges outside the palette stay, unlike in ILBM).
  - **Not part of this ADR:** the Save / Export menu wiring, dialogs and recent-file handling; the integrator does that.
- Deviations from the earlier sketch (ARCHITECTURE §6): deflate PNG layers instead of zstd tiles, `manifest.json` instead of `project.json` + `palette.json`, no `preview.png`, no `source/` of preserved import chunks yet (a project holds what the document model holds). Large multi-layer documents may want tiled blobs later; that would be version 2.
- Verified (run in this worktree):
  - `dpx-formats` unit tests: round trip of the default document, odd sizes (1x1, 7x3, 33x5, 321x257), 2/32/256 colours, AGA 8-plane NTSC HiRes laced 704x480, OCS 16 colours, ranges/grab/transparent/spare; determinism (same bytes twice and after read + write); fixed entry order; manifest content; refusals for newer/zero version, foreign and cut-off files, wrong `format`, unknown field, bad palette, traversal and unsafe names (archive and manifest), missing/extra/directory entries, wrong frame/layer count, tiny limits for entries/total/manifest/pixels, non-PNG, true-colour PNG, 2-bit PNG, wrong size, wrong palette, cut-off PNG, writer refusing pixels outside the palette.
  - App tests: ILBM to `.dpxproj` to ILBM gives identical ILBM bytes; ZIP detected without extension; `.dpxproj` to `.dpxproj` identical bytes; project to PNG reports what PNG drops; open gives the same document and extras (incl. ranges outside the palette); `info` output; cut-off project error.
  - CLI run by hand on a DeluxePaint-era sample (kept outside the repo): `info`, `convert` to `.dpxproj` and back; `cmp` identical for ILBM to `.dpxproj` to ILBM when the first ILBM was written by the app. A raw DeluxePaint file differs after the trip only because the app adds CAMG, aspect and page fields when it writes.
- Not verified: ZIPs from other tools (data descriptors, ZIP64, non-UTF-8 names); projects larger than a few MB; Windows/Linux (macOS only); opening/saving through the GUI; reading by programs other than `unzip` (only `unzip -l` / `-p` were tried).
