# ADR-9: True-colour PNG and JPEG import

- Status: accepted (Phase 2, 2026-11-10)
- Context: Pages are indexed (ADR-1) and limited by the target hardware (OCS LoRes 32 colours with a 12-bit palette, OCS HiRes 16, AGA 256 with 24-bit). Modern pictures (photos as JPEG, RGB/RGBA PNG from current pixel-art tools) carry true colour and alpha. DeluxePaint IV AGA itself reads only IFF; this import is a DeluxePainter addition. The visible behaviour was decided by the owner (2026-11-10).
- Decision:
  - **Reading:** `dpx_formats::read_png` returns `PngImage::Indexed` (palette kept exactly, as before) or `PngImage::TrueColor` for greyscale/RGB with or without alpha, any bit depth (16-bit keeps the high byte; a tRNS colour key becomes alpha). `dpx_formats::read_jpeg` decodes baseline/progressive JPEG to RGB with `zune-jpeg` (MIT/Apache-2.0/Zlib) and applies the EXIF orientation (tags 1–8, parsed by us, malformed EXIF ignored). Both refuse pictures above 64 megapixels. Colour profiles and gamma are ignored. Pictures are recognised by content (`FF D8 FF` = JPEG), not by name.
  - **Size (owner):** a picture that fits a screen format (at most 1280×512) keeps its size; the mode is guessed from the size like an ILBM without CAMG (ADR-7), so the PNG pixel grid is taken as Amiga pixels. A bigger picture is scaled down to the *current* screen (mode and chipset kept), keeping its proportions on that screen's pixel shape (`resample::fit_size`), by area averaging with premultiplied alpha (`resample::scale_area`). A note names the old and new size.
  - **Palette (owner):** a new palette with as many colours as the mode allows (AGA 256, OCS LoRes 32, OCS HiRes 16). A picture with no more colours keeps them exactly (OCS: rounded to 12-bit values, merged where they meet, no dithering). Otherwise `dpx_core::quantize` builds the palette by variance-based median cut on a 6-bit-per-channel histogram (each bin keeps its exact mean), refines it with three k-means passes, and rounds it to the palette depth. Distances are weighted RGB (2·ΔR² + 4·ΔG² + 3·ΔB²).
  - **Dithering (owner):** Floyd–Steinberg, serpentine, error clamped to the colour range; transparent pixels neither take nor pass on error.
  - **Transparency (owner: "magic pink"):** pixels with alpha < 128 become colour 0, which is reserved for them and set to pink #FF00FF so transparent areas stay visible; opaque pixels never use it. The document's transparent colour is set to 0, so an ILBM save writes masking 2 (transparent colour) with colour 0, matching DeluxePaint's "background colour is transparent". Pink pixels in pictures without alpha are not made transparent (that would be guessing).
  - **Palette order:** (reserved colour 0,) the most used colour, then dark to light; padded with black to a power of two (whole bitplanes). Padding entries are never used by pixels.
  - **Where:** pixel algorithms (`quantize`, `resample`, `RgbaImage`) live in `dpx-core`, decoders in `dpx-formats`; the app decides size and target (`files::reduce_true_color`). Picture ▸ Load reduces for the current screen; `--open` and the CLI (`info`, `convert`) use the default screen (AGA PAL LoRes). `info` prints how a true-colour file would open.
  - **Verified:** unit tests for decoders (self-made fixtures in `crates/dpx-formats/tests/data/`), EXIF orientation, resampling, quantisation (exactness, OCS 12-bit entries, transparency, block-mean error), loading through the requester. Six DeluxePaint-era ILBMs from the local `Examplepics/` folder (not in the repo) converted to RGB PNG and loaded again came back pixel-exact. Release timing on a synthetic 4032×3024 JPEG: 0.37 s for decode, scale to 320×240 and reduce to 256 colours; 1280×512 without scaling: 0.43 s. CMYK/YCCK and progressive JPEGs are untested (no fixtures).
- Consequences:
  - Load is still not undoable (ADR-8).
  - A page smaller than the screen shows colour 0 around it; for transparent pictures that is pink. DeluxePaint pages are at least screen size; this is solved with "pages larger than the screen, overscan, custom sizes" (next Phase 2 item).
  - The colour used for transparent pixels is a parameter (`ReduceOptions::transparent`); choosing it in the UI (owner idea, 2026-11-10) comes with palette editing in Phase 3.
  - Brushes from true-colour files will reuse the same reduction (against the picture palette) in Phase 3.
